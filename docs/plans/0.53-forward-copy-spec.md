## 1. One sentence

With default-off capability `forward_send` (plus `send`) enabled, an MCP client can prepare a
draft that forwards — or copies without attribution — exactly one existing message from one
chat to one other chat, the owner approves the exact preview in the local dialog, and the broker
makes one `forwardMessages` attempt whose outcome is visible through `get_send_status`.

## 2. Input → output

| | what | format |
|---|---|---|
| input | `prepare_forward_send`: `source_chat` (same recipient selector forms `prepare_text_send` accepts), `source_message_id` (positive int53), `recipient` (same forms), `mode` (`"forward"` \| `"copy"`), `remove_caption` (bool, default false, only valid with `copy`) | MCP tool arguments, `extra=forbid` |
| output | `ForwardDraftPreview`: `draft_id`, `expires_at`, `mode`, `remove_caption`, `source` (chat id + sanitized title, message id, typed untrusted sender, date, content kind, untrusted text/caption evidence or media identity, `source_sha256`), `recipient` (id + sanitized title), `preview_sha256` | new closed pydantic models |
| input | `send_prepared_forward`: `draft_id`, `approved` (strict bool) | MCP tool arguments |
| output | the existing send result shape (`sent` / `pending` / `failed` / `local_failed` / `not_approved` / `outcome_unknown` / `expired` / `recipient_changed`) plus forward-specific refusals `source_changed`, `source_not_forwardable`, `protected_content` | reuse the existing send-result model if it fits without changing its schema; otherwise a new closed model |

**New data:** forward drafts live in the existing in-memory draft registry (`outgoing_drafts.py`)
with the same owner binding (`DraftOwner(client_id, account_id)`), TTL, single-use claim, receipt
and reconcile machinery, under a new internal kind. They are **not** exposed through
`list_drafts`/`get_draft`/`update_draft`/`refresh_draft`/`cancel_draft` in v1 (those schemas stay
byte-identical); preparing again supersedes, TTL expires.

**Source projection** (`forward_sources.py`, new): canonical JSON ≤ 64 KiB of the source message:
chat id, message id, typed sender, date, edit date, content kind, text or caption (with entity
types/offsets/lengths), and for file-backed content: file size and `sha256(remote.unique_id)` per
file (never file ids or local paths), plus duration/width/height/mime/file name where the content
type has them. `forward_info` is allowed (forwarding a forward). `source_sha256` = sha256 of the
projection. Supported content: `messageText`, `messagePhoto`, `messageDocument`, `messageVoiceNote`,
`messageVideo`, `messageAudio`, `messageAnimation`. Anything else → `unsupported_source_content`.
Self-destructing, ephemeral, scheduled or still-sending sources → `unsupported_source_state`.

## 3. Scenario

```
prepare_forward_send(source_chat=<A>, source_message_id=<m>, recipient=<B>, mode="copy")
  → ForwardDraftPreview (shown to the user by the client)
send_prepared_forward(draft_id=<d>, approved=true)
  → local macOS dialog shows the exact forward preview → owner clicks Send
  → {"status": "pending" | "sent", ...}
get_send_status(draft_id=<d>) → sent | failed | unknown, with evidence strength
```

**Prepare (broker):** require `send` + `forward_send` → owner → resolve source chat and recipient
(secret chats refused via the existing verified-target identity rules; source ≠ recipient is
allowed) → `getMessage(source)` → projection (refusals above) → `getMessageProperties(source)`:
`forward` needs `can_be_forwarded`, `copy` needs `can_be_copied`; any
`has_protected_content_by_current_user/other_user` or source `chat.has_protected_content` →
`protected_content` → create draft, store sanitized titles.

**Send (broker), same order as `_send_prepared_artifact_impl`:** `approved is True` else
`not_approved` → owner/policy → kind → stored receipt replay → title map (restart ⇒ `expired`) →
recipient re-resolve + title compare (`recipient_changed`) → source re-read: projection hash equal
(`source_changed`) and properties still allow (`source_not_forwardable` / `protected_content`) →
approval dialog → owner/policy/epoch recheck → single-use claim → `tdjson.forward_message` →
finish/receipt. Errors: `MessageSendNotAttempted` ⇒ `local_failed`; provider error ⇒ `failed`;
anything else ⇒ `outcome_unknown`. **Never retry.**

**TDLib:** add `forwardMessages` to `_ALLOWED_REQUEST_TYPES` with a closed shape validated in
`_validate_bounded_request`: `chat_id`, `topic_id: null`, `from_chat_id`, `message_ids` of length 1,
`options` exactly `{"@type":"messageSendOptions","suggested_post_info":null,
"disable_notification":false,"from_background":false,"protect_content":false,
"allow_paid_broadcast":false,"paid_message_star_count":0,
"update_order_of_installed_sticker_sets":false,"scheduling_state":null,"effect_id":0,
"sending_id":<random int32 ≠ 0>,"only_preview":false}`, `send_copy` bool, `remove_caption` bool
(false unless `send_copy`). The result must be `messages` with exactly one message in the
recipient chat; it is registered with send observations by `sending_id` + chat + returned
temporary message id (content-hash matching does not apply to forwards). Final state comes from
`updateMessageSendSucceeded/Failed` like other sends.

**Approval dialog:** a new mutually exclusive preview channel `forward` in `approval_prompt.py`
showing: the mode in words (`FORWARD — recipients see the original sender` /
`COPY — sent as your own message, no attribution` [+ `caption removed`]), source chat title and
id, message id, sender (marked untrusted), date, content kind, escaped text/caption marked
untrusted or media name/size, `source_sha256`, recipient title and id, `preview_sha256`.

**Capability plumbing:** `forward_send` in `config.KNOWN_CAPABILITIES` (not in legacy defaults),
`OPERATION_CAPABILITIES`, `broker_protocol.OPERATIONS`, `server._TOOL_NAMES`, the three hard-coded
"also requires `send`" sets, manifest tool/forbidden lists, `.codex/config.toml.example`.

## 5. Out of scope

Multiple messages and albums (F15), forum-topic destinations (`topic_id` stays null), retained-
selection sources, scheduling, paid messages, forwarding to secret chats, caption editing on copy,
exposing forward drafts through the generic draft tools.

## 8. Risks and degradation

- A provider-side change in `forwardMessages` result shape ⇒ `outcome_unknown`, never a retry.
- Telegram may silently convert a forward to a copy for some chats; the receipt records what was
  requested, and status evidence reports what the provider returned.
- Protected-content rules may tighten; any `false` property or protected flag refuses.

**Ceiling:** three distinct failed hypotheses on one sub-step ⇒ stop and record in the tasks file.
