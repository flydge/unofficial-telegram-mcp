# 0.53 F14 — exact forward/copy of one message — implementation spec

**Status:** accepted 16.10.2026 under the owner's overnight delegation ("finish development
following the plan"); **owner review pending**. Decisions below were made by the lead without
an interview; the owner may amend them in a separate commit.
**Branch:** `qr-onboarding-052` (continues after 0.52 phases A–E; F14 is independent code)
**Tasks:** [`0.53-forward-copy-spec.tasks.md`](0.53-forward-copy-spec.tasks.md)
**Requirement:** original plan F14 ([initial-roadmap](initial-roadmap.md)): "exact source/destination,
explicit forward-versus-copy semantics, protected-content checks, source revalidation and one
transport attempt with a receipt."

---

## 1. One sentence

With default-off capability `forward_send` (plus `send`) enabled, an MCP client can prepare a
draft that forwards — or copies without attribution — exactly one existing message from one
chat to one other chat, the owner approves the exact preview in the local dialog, and the broker
makes one `forwardMessages` attempt whose outcome is visible through `get_send_status`.

## 2. Input → output

| | what | format |
|---|---|---|
| input | `prepare_forward_send`: `source_chat` (same recipient selector forms `prepare_text_send` accepts), `source_message_id` (positive int53), `recipient` (same forms), `mode` (`"forward"` \| `"copy"`), `remove_caption` (bool, default false, only valid with `copy`) | MCP tool arguments, `extra=forbid` |
| output | `ForwardDraftPreview`: `draft_id`, `expires_at`, `mode`, `remove_caption`, `source` (chat id + sanitized title, message id, typed untrusted sender, date, content kind, untrusted text/caption evidence or media identity, `source_sha256`), `recipient` (id + sanitized title), `preview_sha256` | new closed pydantic models |
| input | `send_prepared_forward`: `draft_id`, `approved` (strict bool) | MCP tool arguments |
| output | the existing send result shape (`sent` / `pending` / `failed` / `local_failed` / `not_approved` / `outcome_unknown` / `expired` / `recipient_changed`) plus forward-specific refusals `source_changed`, `source_not_forwardable`, `protected_content` | reuse the existing send-result model if it fits without changing its schema; otherwise a new closed model |

**New data:** forward drafts live in the existing in-memory draft registry (`outgoing_drafts.py`)
with the same owner binding (`DraftOwner(client_id, account_id)`), TTL, single-use claim, receipt
and reconcile machinery, under a new internal kind. They are **not** exposed through
`list_drafts`/`get_draft`/`update_draft`/`refresh_draft`/`cancel_draft` in v1 (those schemas stay
byte-identical); preparing again supersedes, TTL expires.

**Source projection** (`forward_sources.py`, new): canonical JSON ≤ 64 KiB of the source message:
chat id, message id, typed sender, date, edit date, content kind, text or caption (with entity
types/offsets/lengths), and for file-backed content: file size and `sha256(remote.unique_id)` per
file (never file ids or local paths), plus duration/width/height/mime/file name where the content
type has them. `forward_info` is allowed (forwarding a forward). `source_sha256` = sha256 of the
projection. Supported content: `messageText`, `messagePhoto`, `messageDocument`, `messageVoiceNote`,
`messageVideo`, `messageAudio`, `messageAnimation`. Anything else → `unsupported_source_content`.
Self-destructing, ephemeral, scheduled or still-sending sources → `unsupported_source_state`.

## 3. Scenario

```
prepare_forward_send(source_chat=<A>, source_message_id=<m>, recipient=<B>, mode="copy")
  → ForwardDraftPreview (shown to the user by the client)
send_prepared_forward(draft_id=<d>, approved=true)
  → local macOS dialog shows the exact forward preview → owner clicks Send
  → {"status": "pending" | "sent", ...}
get_send_status(draft_id=<d>) → sent | failed | unknown, with evidence strength
```

**Prepare (broker):** require `send` + `forward_send` → owner → resolve source chat and recipient
(secret chats refused via the existing verified-target identity rules; source ≠ recipient is
allowed) → `getMessage(source)` → projection (refusals above) → `getMessageProperties(source)`:
`forward` needs `can_be_forwarded`, `copy` needs `can_be_copied`; any
`has_protected_content_by_current_user/other_user` or source `chat.has_protected_content` →
`protected_content` → create draft, store sanitized titles.

**Send (broker), same order as `_send_prepared_artifact_impl`:** `approved is True` else
`not_approved` → owner/policy → kind → stored receipt replay → title map (restart ⇒ `expired`) →
recipient re-resolve + title compare (`recipient_changed`) → source re-read: projection hash equal
(`source_changed`) and properties still allow (`source_not_forwardable` / `protected_content`) →
approval dialog → owner/policy/epoch recheck → single-use claim → `tdjson.forward_message` →
finish/receipt. Errors: `MessageSendNotAttempted` ⇒ `local_failed`; provider error ⇒ `failed`;
anything else ⇒ `outcome_unknown`. **Never retry.**

**TDLib:** add `forwardMessages` to `_ALLOWED_REQUEST_TYPES` with a closed shape validated in
`_validate_bounded_request`: `chat_id`, `topic_id: null`, `from_chat_id`, `message_ids` of length 1,
`options` exactly `{"@type":"messageSendOptions","suggested_post_info":null,
"disable_notification":false,"from_background":false,"protect_content":false,
"allow_paid_broadcast":false,"paid_message_star_count":0,
"update_order_of_installed_sticker_sets":false,"scheduling_state":null,"effect_id":0,
"sending_id":<random int32 ≠ 0>,"only_preview":false}`, `send_copy` bool, `remove_caption` bool
(false unless `send_copy`). The result must be `messages` with exactly one message in the
recipient chat; it is registered with send observations by `sending_id` + chat + returned
temporary message id (content-hash matching does not apply to forwards). Final state comes from
`updateMessageSendSucceeded/Failed` like other sends.

**Approval dialog:** a new mutually exclusive preview channel `forward` in `approval_prompt.py`
showing: the mode in words (`FORWARD — recipients see the original sender` /
`COPY — sent as your own message, no attribution` [+ `caption removed`]), source chat title and
id, message id, sender (marked untrusted), date, content kind, escaped text/caption marked
untrusted or media name/size, `source_sha256`, recipient title and id, `preview_sha256`.

**Capability plumbing:** `forward_send` in `config.KNOWN_CAPABILITIES` (not in legacy defaults),
`OPERATION_CAPABILITIES`, `broker_protocol.OPERATIONS`, `server._TOOL_NAMES`, the three hard-coded
"also requires `send`" sets, manifest tool/forbidden lists, `.codex/config.toml.example`.

## 5. Out of scope

Multiple messages and albums (F15), forum-topic destinations (`topic_id` stays null), retained-
selection sources, scheduling, paid messages, forwarding to secret chats, caption editing on copy,
exposing forward drafts through the generic draft tools.

## 8. Risks and degradation

- A provider-side change in `forwardMessages` result shape ⇒ `outcome_unknown`, never a retry.
- Telegram may silently convert a forward to a copy for some chats; the receipt records what was
  requested, and status evidence reports what the provider returned.
- Protected-content rules may tighten; any `false` property or protected flag refuses.

**Ceiling:** three distinct failed hypotheses on one sub-step ⇒ stop and record in the tasks file.

### Amendments 16.10.2026 (critic review)

Lead decisions on the independent critic review of 34e6a16. Each decision H1–INFO has a test in
`tests/test_forward_send.py::CriticReviewTests` that fails on 34e6a16 and passes after. They
supersede the §2/§3 text where they differ. Projection version 2 and preview digest version 2
replace version 1 (drafts are in-memory only; no migration).

- **H1 — hidden content refuses.** A new content-free refusal `hidden_source_content` applies when
  the text or caption carries any entity type outside the explicit allowlist of fieldless visible
  types (Bold, Italic, Underline, Strikethrough, Spoiler, Code, Pre, BlockQuote,
  ExpandableBlockQuote, Mention, Hashtag, Cashtag, BotCommand, Url, EmailAddress, PhoneNumber,
  BankCardNumber), or an allowlisted type with any field. TextUrl, MentionName, CustomEmoji,
  PreCode (language), MediaTimestamp, DateTime and unknown types are refused. A non-null
  `reply_markup` and `link_preview_options` whose non-empty `url` is not literally present in the
  visible text also refuse. Entities must be exact `textEntity` records on whole-scalar UTF-16
  boundaries of the raw text (otherwise `unsupported_source_content`). Admitted
  `link_preview_options` are projected (hashed) and shown. The earlier test asserting that a TextUrl
  target is absent from the preview is replaced by refusal tests.
- **M1 — forward of a forward; attribution fields.** With `mode="forward"` a source with non-null
  `forward_info` refuses `source_is_forward` (nested attribution is not shown); `copy` allows it
  (no attribution is sent) and the preview/dialog say the source is itself a forward. §2's
  "`forward_info` is allowed" is narrowed accordingly; only `is_forward` is projected.
  `author_signature` and `via_bot_user_id` are required scalars, projected (hashed) and shown when
  non-empty/non-zero.
- **M2 — reversible display.** Preview and dialog show the outgoing text/caption as the marked
  reply-v23 reversible JSON escape (`reply_formatted_sources._inert_json_string`: only ASCII
  letters, digits, `_` and `-` literal), so homoglyphs, bidi/zero-width controls and whitespace
  appear as `\uXXXX`. Decoding one JSON layer yields exactly the raw hashed text; entity offsets
  address that raw text in UTF-16 code units, and the dialog lists each entity with its escaped
  covered span. `text_sanitized` is removed. Escaped text is bounded by 12×4096+2 characters
  (never refuses a valid source); escaped text plus covered spans above 131072 characters refuses
  `unsupported_source_content`. Short names (file name, MIME type, audio title/performer, author
  signature) stay marked sanitized evidence; a non-blank name that sanitizes to nothing refuses
  `hidden_source_content`, one longer than 255 displayed characters refuses
  `unsupported_source_content`.
- **M3 — re-prepare supersedes.** Preparing a forward draft marks the same owner's pending forward
  draft for the same (source chat, message ID, recipient, mode, remove_caption) superseded; it can
  no longer be claimed (send returns `expired`, no dialog, no attempt). Other keys and other owners
  are unaffected. The tool description says so and states that generic draft tools still cannot
  list, update, refresh or cancel forward drafts.
- **L1 — Saved Messages.** When the recipient is the account's own Saved Messages (chat ID and
  private-chat user ID equal the account ID), the provider's `is_outgoing=false` on the returned
  message is accepted provided sending_id, chat and temporary ID all match. Elsewhere an incoming
  flag never matches.
- **L2 — early success.** If `updateMessageSendSucceeded` arrives before the `forwardMessages`
  result, the attempt still waits (existing deadline) for the result and validates it; only then is
  `sent` returned. A malformed or mismatched result — before or after an early success — turns the
  observation into a terminal `conflict`: the attempt returns `outcome_unknown` and later
  `get_send_status` never reconciles it to `sent`. A lost result after an early success returns
  `outcome_unknown`; later status may still report the provider-confirmed final message.
- **L3 — presentation fields.** Audio `title` and `performer`; photo/video/animation `has_spoiler`
  and `show_caption_above_media`; video `start_timestamp` are required, projected and shown.
  Thumbnails, album covers, video covers, storyboards and alternative videos stay unprojected and
  undisplayed (the provider copies them; they cannot be reviewed in the dialog).
- **L4 — auto-delete.** `auto_delete_in` is a required scalar; any non-zero value refuses
  `unsupported_source_state`.
- **L5 — remove_caption.** `remove_caption=true` with a `messageText` source refuses with the new
  content-free code `invalid_input` at prepare. For media with `remove_caption`, the dialog shows
  `Caption: removed — not sent` instead of the caption text (the MCP preview still carries the
  source caption evidence that is hashed).
- **INFO.** The dialog shows account, draft ID and expiry like the other send dialogs;
  `account_id` is part of the preview and its digest. The receipt replay for a local failure says
  no provider attempt was made.
- **Send-time refusals.** A send-time eligibility refusal other than `source_not_forwardable` or
  `protected_content` is reported as `source_changed` (the projection binds the facts behind the
  new prepare-time codes), so the send result schema is unchanged.
- **Residual.** Reversible escapes make non-Latin text (for example Cyrillic) hard to read in the
  dialog; `import_info` sources are not refused; real delivery (criterion 10) remains deferred to
  the owner.

### Amendments 16.10.2026 (docs alignment)

- The approval **dialog** shows text and captions readable in any script, marking only
  invisible, bidi, NFKC-unstable and mixed-script (Cyrillic/Greek inside an ASCII word)
  characters as reversible `⟦U+XXXX⟧`; the MCP **preview** keeps the reversible JSON escapes.
  This supersedes the dialog part of amendment M2.
- Secret source or recipient chats return the content-free `unavailable` status (no refusal code).
- `send_prepared_forward` never returns `pending`; an unconfirmed outcome is `outcome_unknown`
  and `get_send_status` reconciles it.

### Amendments 16.10.2026 (re-review)

Lead decisions on the independent re-review of fd47384. Each decision D1–D5 has a test in
`tests/test_forward_send.py::ReReviewTests` that fails on fd47384 and passes after; D6 adds the
listed tests. They supersede the earlier text where they differ. Projection version 3 (text
sources gain the link-card URL) and preview digest version 3 (the preview gains
`link_preview_card_url`) replace version 2; drafts are in-memory only, so there is no migration.

- **D1 — more marks in the dialog.** `readable()` additionally renders as reversible `⟦U+XXXX⟧`:
  every Unicode 16 Default_Ignorable_Code_Point (hard-coded: 00AD, 034F, 061C, 115F–1160,
  17B4–17B5, 180B–180F, 200B–200F, 202A–202E, 2060–206F, 3164, FE00–FE0F, FEFF, FFA0, FFF0–FFF8,
  1BCA0–1BCA3, 1D173–1D17A, E0000–E0FFF) except a single U+FE0E or U+FE0F directly after a
  character that is not a variation selector and not followed by one (ordinary emoji
  presentation stays literal); U+2800; each combining mark (Mn/Me) after the second in a
  consecutive run; each U+0020 after the first in a run; and U+301A/U+301B next to the already
  marked U+27E6. All earlier rules remain.
- **D2 — look-alike letters.** Inside a whitespace-delimited word that also has ASCII letters,
  letters whose Unicode name starts with CYRILLIC, GREEK, ARMENIAN, CHEROKEE or LISU, and
  non-ASCII LATIN letters without a canonical decomposition (ɡ, ı, ɑ, also ß, ł, ø), are marked;
  é or ü decompose and stay literal. Look-alike words written entirely in one script stay
  literal (documented limitation). The rule is stated exactly once (`READABLE_RULE`), in the
  `readable()` and `_forward_detail` docstrings, in a dialog legend line and in the docs; no text
  claims that nothing can hide.
- **D3 — delimited spans.** The dialog encloses the text or caption body, each entity's covered
  text and each link-preview URL in `« … »`, under the legend line `Untrusted spans in « » below
  are exact; <rule>.`; the text label becomes `Text|Caption [untrusted Telegram evidence] (exact):`.
  `readable()` marks literal « and » (U+00AB/U+00BB), so untrusted content cannot close a span;
  line breaks (Cc, U+2028, U+2029) are marked, so it cannot start a dialog line.
- **D4 — link-preview URLs.** `link_preview_options.url` (when non-empty) and the `url` of the
  message's `link_preview` card (when the card is present) must each equal exactly either the
  covered text of a `textEntityTypeUrl` entity or a whole whitespace-delimited token of the
  visible text; otherwise `hidden_source_content`. A prefix, a substring of a longer link or an
  empty card URL refuses; a malformed card is `unsupported_source_content`. The card URL is
  projected, bound by `source_sha256`, carried as `source.link_preview_card_url` and shown on a
  `Link preview card` dialog line; a card that appears or changes after preparation is
  `source_changed`. The card's title, description, site name and media are neither projected
  nor shown. The proxy-side preview model applies the same rule. The 131072-character evidence
  bound now also counts the escaped link-preview URLs.
- **D5 — names.** A file name, MIME type, audio title or performer, or author signature that
  `sanitize_telegram_text` would change (removed controls or bidi characters, NFKC changes,
  collapsed, leading or trailing whitespace) refuses `hidden_source_content`; an unchanged name
  longer than 255 characters refuses `unsupported_source_content`. Admitted names are therefore
  shown exactly; the preview and digest model is otherwise unchanged.
- **D6 — tests.** `ReadableDialogTextTests` now runs above the `__main__` guard; a draft
  superseded while its dialog is open returns `expired` with zero `forwardMessages`; link-card
  tests, the repeated-space, U+2800, variation-selector, combining-run and 〚 cases, and
  reversibility of every new mark are covered.
- **Residual (added).** The link card's title, description, site name and media are delivered
  but not shown. A provider that normalizes the card URL (for example adds a scheme to a bare
  domain) makes a legitimate message refuse until real-provider evidence says otherwise. A single
  U+FE0E/U+FE0F after an arbitrary non-selector character stays literal (a low-bandwidth
  channel). Dialog word wrapping can still place untrusted words at the start of a visual line
  inside a « » span. Pure-script look-alike words stay literal, and legitimate undecomposed Latin
  letters (ß, ł, ø, æ) are marked when mixed with ASCII letters.
