## 1. One sentence

A user without developer tools downloads one signed, notarized DMG, double-clicks `Install.command`,
scans a QR code, and then has the same Telegram MCP registered in Claude Code, Codex and Claude Desktop
(or as a Claude Code plugin). The build is reproducible from tracked scripts and pinned inputs, and it can
be upgraded, rolled back and uninstalled without touching the Telegram session.

## 2. Input → output

| | what | format |
| --- | --- | --- |
| input | the checkout at a tag, pinned PBS CPython, the hash-locked wheel closure, the TDLib/OpenSSL kegs matching the lock, the build Mac's signing identity and notary profile (owner) | files, Keychain |
| output | `<name>-<version>-macos-arm64.dmg` (signed, notarized, stapled) with `Install.command`, `bootstrap.sh`, the signed seed, `release.tar.gz`, `release-index.json`, `release-pins.json`, `SHA256SUMS`; a corresponding-source archive; release-gate evidence | files |
| output | client registrations: Codex TOML subtree, Claude Code user scope **or** plugin, Claude Desktop `mcpServers` entry; skills | owned entries with receipts |

## 3. Phases and work items

### A — product identity (no behaviour change)

- `product_identity.py` holds every user-visible name: display name, MCP server name, plugin name and
  plugin server name, marketplace name, codesign identifier prefix, bundle root name, DMG volume name and
  Telegram device model.
- All user-visible strings in `src/` come from it. A rename-impact test allows legacy names only on an
  explicit list, and a name-constraint checker enforces the plugin limit: the plugin name plus the plugin
  server name is at most 20 characters, so every `mcp__plugin_<plugin>_<server>__<tool>` stays within 64.
- Fix the stale TDLib `device_model` and `application_version` in `tdjson.py`.
- Internal compatibility names stay: Python package, `TelegramSearchMCP` paths, Keychain service, launchd
  labels and environment keys. The placeholder plugin name `telegram-local` with server `tg` stands until
  the owner names the product.

### B — reproducible payload and grammar

- `packaging/prepare_native.py` reproduces `packaging/tdlib-lock.json` from the kegs ("homebrew-receipt-
  relocated"), checks the `td_api.tl` hash against `schema_sha256` and refuses a wrong keg or a stray rpath.
- `packaging/prepare_payload.py` builds the whole payload from pinned inputs, with no `~/.codex` reference.
  It prunes what the product never uses (Tcl/Tk, `_tkinter`, idle, `include/`, `share/`, pip, and the
  duplicate `python` and `python3.14` executables) and records the Mach-O inventory, counted by magic, in
  provenance. Two builds from the same inputs are identical.
- Manifest v2: `publication` `unreleased|published`, `source_completeness` `incomplete|complete`,
  `publisher {kind: adhoc|developer-id, team_id}`. v1 stays admitted. The launcher's admitted version is
  generated from `__version__` at payload build time.
- Lock v2 with a reviewed allowlist table of approved pins. For each signed artifact it records the
  shipped bytes and sha256 and the unsigned ones, which must equal the v1 pins, plus the signature kind and
  team id. `native_runtime` verifies the Developer ID designated requirement with the Team ID.
- The Homebrew/source path gets the synchronous TDLib version and commit probe the bundle path already
  runs; `--check` reports the OpenSSL keg.

### C — signing and distribution pipeline

- `packaging/sign_payload.py` signs every Mach-O inside out: `--timestamp --options runtime`, explicit
  stable identifiers, and minimal entitlements proven by a matrix test (never
  `allow-dyld-environment-variables`). The identity `-` (ad hoc) is used in tests.
- The seed is signed with Developer ID. `bootstrap.sh` gains an optional `--seed-team` that checks the
  designated requirement before executing the seed. Quarantine on the staged seed is kept, so Gatekeeper
  evaluates the notarized seed. The sha256 and index pins stay.
- `packaging/notarize_release.sh`: notarize the signed payload zip, build the DMG, sign, notarize and
  staple it. `notarytool` is mocked in tests and never called without the owner's keychain profile.
- `Install.command` runs the pinned `bootstrap.sh` in native Terminal. Then it runs the activation command
  with `connect` **inline in the same Terminal**: the QR page opens, the user scans, and Terminal prints the
  final result. One double-click covers install and login, which also serves shell-less clients.
- `packaging/release_build.py` orchestrates payload → sign → repin → assemble → seed → notarize/DMG →
  sums, pins, provenance and SBOMs → the corresponding-source archive. The release gate gains a bundle stage.
- `packaging/signing_preflight.sh` and an owner checklist check the Developer ID identity and the notary
  profile, printing only non-secret results.
- An assembly switch builds without the application identity, or with an identity from a named Keychain
  service. Which identity a public bundle carries is the owner's decision.

### D — clients

- **Claude Desktop registration** (`claude_desktop_registration.py`). It writes an owned `mcpServers`
  `telegram_search` entry in `claude_desktop_config.json`:
  - a bounded, no-follow, strict-JSON read; an owner-owned file that is not group or world writable (0644
    allowed);
  - a journaled compare-before-replace write; neighbours preserved, or the install refuses;
  - an ownership receipt;
  - a different existing entry refuses the whole install before anything is created; skipped when Claude
    Desktop is absent;
  - the result tells the user to restart Claude Desktop.
- **Server instructions and manifest.** A client-neutral `instructions` string of at most 2,500
  characters: start with `_manifest`, routing, untrusted data, the answer format, actions, recovery. The
  `_manifest` gains `available_tools` and `tool_capabilities`. Client-specific wording ("Codex supplies…")
  becomes client-neutral.
- **Policy-filtered `tools/list`.** Only tools usable under the loaded policy are listed. The schema
  fingerprint keeps covering the full registration, so compatibility checks do not change. Tool-count
  assertions are derived from the registration.
- **Claude Code plugin and marketplace.** The repo root holds `.claude-plugin/marketplace.json`. The plugin
  directory has:
  - `plugin.json` with the product version;
  - `.mcp.json` that runs `bin/mcp-entry`, a `/bin/sh -p` shim that selects the installed release from
    `current.json` and execs the launcher under `env -i`;
  - generated byte-identical skill copies.

  The installer gains `--claude-code plugin|user|skip`. In plugin mode it skips the user-scope entry and
  the `~/.claude/skills` copies. A plugin-driven runtime install from the pinned public release is built
  and tested against a local stub.
- **Recording shim.** A structural STDIO recorder for client evidence. It records the protocol revision,
  client name, the tool census and fingerprint, and per-call tool name and `isError`. It never records
  arguments or results.

### E — upgrade, rollback, uninstall, migration

- An `upgrade` transaction:
  - publishes the new release next to the current one;
  - re-registers owned client entries and republishes the skills;
  - rewrites the broker plist;
  - checks pending sends before restarting only the exact receipt-bound broker;
  - rewrites only the `expected_package_version` line of `runtime.toml`;
  - switches `current.json` last.

  The enrollment, managed key, session and capabilities stay byte-identical.
- `rollback` to the previous release, when no newer state would be refused.
- `uninstall` removes only owned objects. The session and Keychain are never touched.
- Migration of entries the installer does not own (for example a 0.51 `telegram_search` entry in Claude
  Desktop or Codex, or a source-venv broker plist): an explicit `--adopt-legacy` path. It replaces the
  foreign entry only after it is recorded and backed up in the receipt, and only when the owner runs it.

Owner migration command: with `KIT` the absolute path of the kit folder and the pins from its
`release-pins.json`, run `/usr/bin/env -i /bin/sh -p "$KIT/bootstrap.sh" --seed "$KIT/bootstrap-verifier"
--seed-sha256 <seed_sha256> --seed-bytes <seed_bytes> --archive "$KIT/release.tar.gz" --index
"$KIT/release-index.json" --trusted-index-sha256 <index_sha256> --seed-team <team_id> --adopt-legacy`
(`--seed-team` only when the pins carry a Team ID), then the printed activation command. `--adopt-legacy`
is accepted only as the final token and reaches the launcher as its last token; `Install.command` and the
plugin never pass it. A pending send on the legacy broker refuses before anything is created; every backup
is listed in the root's `adopted.json` and kept beside the root on uninstall.

## 5. Out of scope

Windows/Linux, an MCPB desktop extension (rejected below), Streamable HTTP (F19), multiple accounts
(0.55), CI-based signing.

## 6. Decisions and rejected options

- **Container: a DMG with `Install.command`.** A flat `.pkg` was rejected: it runs as the system installer,
  which conflicts with the per-user, owner-only design. A zip was rejected because it cannot be stapled.
- **Trust root: keep the sha256 and index pins and add a Team ID check.** Replacing the pins with the Team
  ID alone was rejected: it would trust anything the team ever signs.
- **Quarantine on the staged seed: kept.** Stripping it would make offline installs work but bypass
  Gatekeeper.
- **How clients point at the runtime.** Exact release paths for Codex, Claude Code and Claude Desktop,
  with upgrades rewriting owned entries; only the plugin uses a `current.json` shim. A stable entrypoint
  for everyone was rejected: it is a second trust path.
- **A conflicting Claude Desktop entry refuses the install**, matching Claude Code. Adoption is explicit
  (`--adopt-legacy`).
- **Shell-less onboarding: inline `connect` in `Install.command` plus server instructions.** New MCP setup
  tools were rejected: they would change the schema and tool count without being needed.
- **Plugin vs. user scope are exclusive** (`--claude-code`), because both at once duplicate tool sets.
- **The marketplace lives in the product repo**; the official directory comes only after the rename.
- **Signing runs locally** on the owner's Mac; CI with an exported `.p12` was rejected.
- **MCPB desktop extension rejected for now.** It would add a third packaging channel whose runtime layout
  conflicts with the owner-only broker and launchd design.
- **Pruning standalone Python: yes**, which means fewer Mach-O files to sign and about 55–70 MB less.
- **Policy-filtered `tools/list`: yes, with the full-registration fingerprint unchanged.** Listing all
  tools was rejected, because clients without the skill then try unusable tools.

## 8. Risks

- Hardened runtime and library validation can refuse a dylib at runtime. A Developer ID python changes the
  code identity behind the database-key Keychain ACL. The entitlement matrix and the migration test cover
  this; the real run is at the end.
- Claude Desktop may rewrite its config from memory while running. The status check reports drift, and the
  install asks for a restart.
- Network fetches of pinned inputs are cached once, by hash, outside `/tmp`.

**Ceiling:** three distinct failed hypotheses on one sub-step ⇒ stop and record in the tasks file.
