# 0.57 — own-message actions (F17 rest) — implementation spec

**Status:** lead spec, 21.10.2026, written under the owner's standing delegation. Every decision below is a
**lead decision, owner review pending** (see the [completion plan](completion-plan.md)).
**Branch:** `message-actions-057`, from the 0.56 release candidate.
**Tasks:** [`0.57-own-message-actions-spec.tasks.md`](0.57-own-message-actions-spec.tasks.md)
**Requirement:** F17 rest: own caption edit, styled text and caption edits, pin and unpin, exact deletion
of one own message. Each is its own default-off capability requiring `send` and `read`. F17a (archive,
plain text edit) shipped in 0.52.0 under the `0.54-archive-and-edit` spec.

## 1. One sentence

The owner can edit the caption or the styling of their own message, pin or unpin a message, and delete
exactly one of their own messages for everyone, each after a dialog that states the side effects, with
the final state verified or reported as unknown.

## 2. TDLib facts (pinned d1085f9)

- **Caption edit.** `editMessageCaption chat_id message_id reply_markup caption show_caption_above_media`
  returns `Message`.
  - TDLib trims edge whitespace and accepts an empty caption.
  - It silently drops `show_caption_above_media` where it is not allowed.
- **Pin and unpin.** `pinChatMessage chat_id message_id disable_notification only_for_self` and
  `unpinChatMessage` return `Ok`.
  - Pinning posts a visible service message.
  - `disable_notification` matters only in basic groups and supergroups.
  - A pin that races an existing pin returns a 4xx; it is not reported as not-modified.
- **Delete.** `deleteMessages chat_id message_ids revoke` returns `Ok`.
  - TDLib deletes locally first and emits `updateDeleteMessages` before the server answers.
  - For a message that is not loaded, it answers `ok` without sending anything to the server.
  - After a server failure, it fetches the message again from the server.
  - A 404 after `ok` is answered locally.
  - A logged server delete is replayed after a restart.
- **Delete eligibility** comes from `getMessageProperties`: `can_be_deleted_for_all_users` and
  `can_be_deleted_only_for_self`. In Saved Messages only self-deletion exists.

## 3. Work items

- **First, with no behaviour change: one draft-kind table.** It replaces the isinstance and tuple dispatch
  in `outgoing_drafts.py` and the broker kind tuples. Each kind row carries its change, unbacked and
  dedicated flags and its status policy, with one test per flag.
- **Capabilities.** Each is default off, and each requires `send` and `read`:
  - `edit_own_caption`
  - `edit_own_styled_text`
  - `pin_messages`
  - `delete_own_message`

  A styled caption needs both edit capabilities. `formatted_text_send` stays a sending capability and is
  not required for edits.
- **Tools.**
  - `prepare_text_edit` gains an optional `outgoing_entities`, gated by `edit_own_styled_text`. This is a
    listed schema change.
  - New pairs:
    - `prepare_caption_edit` / `apply_prepared_caption_edit`, with optional entities;
    - `prepare_pin_change(action: pin | unpin)` / `apply_prepared_pin_change`;
    - `prepare_message_delete` / `apply_prepared_message_delete`.
  - The census grows by 6. All new responses use the 0.54 `declined`, `timeout` and `dialog_unavailable`
    statuses and `next_action` from the start.
- **Closed request shapes.**
  - `editMessageCaption`:
    - `reply_markup` is null;
    - `show_caption_above_media` equals the reviewed value;
    - the caption is the reviewed text and entities, or exactly an empty formatted text to remove it.
    - Edge whitespace and NFKC-changing input are refused (as `prepare_text_edit` does), never silently
      rewritten.
  - `editMessageText` with entities: a second shape bound to a styled draft. The plain shape keeps
    `entities == []`.
  - `pinChatMessage`: `only_for_self` is false and `disable_notification` is true, both fixed.
    `unpinChatMessage`: exact keys.
  - `deleteMessages`: exactly one id, `revoke` true, and only when `can_be_deleted_for_all_users` was read
    under the same provider lock.
    - Saved Messages, self-only deletion, scheduled or sending messages, and other people's messages are
      refused.
    - `deleteChatHistory`, the by-sender and by-date deletes and `unpinAllChatMessages` stay unreachable.
  - Exact-set tests cover the allowlist, the change set and the `_call` refusals.
- **Snapshots and verification.**
  - Caption edit:
    - the snapshot is the own media message (photo, video, animation, document, audio, voice note), with
      its caption, entities and above-media flag;
    - the result must be the same message, of the same content kind, with exactly the new caption and
      the caller's style spans, allowing only auto-detected extras.
  - Styled edit: the same rule for text.
  - Pin: the snapshot adds `is_pinned` and `can_be_pinned`. The final state is a bounded
    `getMessage.is_pinned` poll. A 4xx gets a read-back that classifies it as already pinned, not pinned,
    or failed.
  - Delete:
    - it is `applied` only when `ok` follows a successful locked `getMessage`;
    - after a 4xx, a read-back that finds the message on the server means `failed`, and anything else is
      `outcome_unknown`;
    - the generic "4xx proves no change" rule is not used for delete;
    - restart replay of an unknown delete is disclosed.
- **Dialogs**, on the 0.54 renderer model:
  - The delete dialog has a `Delete` button and states that the deletion is irreversible, removes the
    message for every participant, and unpins it if pinned.
  - The pin dialog states that a visible service message is posted.
  - The caption dialog shows the old and new caption, or "Remove caption".
- **Hidden caption entities.** Captions with TextUrl, CustomEmoji or MentionName stay refused as hidden
  content until the 0.58 families land.

## 5. Decisions and rejected options

- **Delete for everyone only, in v1.** Self-only deletion in Saved Messages is permanent loss with no
  counterpart for the recipient. It is refused until the owner asks for it.
- **Pin is silent and never self-only.** A notification is a broadcast side effect the dialog cannot fully
  convey.
- **Removing a caption is allowed, in one pinned form.** The empty formatted text is used, never null.
- **Styled text extends `prepare_text_edit`**, not a separate pair. One edit tool is easier for models; the
  schema change is listed.

## 6. Risks

- Delete is irreversible. The dialog is the only real gate, and `approved=true` from the model is never
  authority.
- Auto-detected entities could make verification report `outcome_unknown` unless they are tolerated
  exactly.

**Ceiling:** three distinct failed hypotheses on one sub-step ⇒ stop and record.

### Part 1 (draft-kind table, capabilities, caption edit) — lead decisions, owner review pending

- **Draft-kind table** (`draft_kinds.DRAFT_KINDS`): one row per kind with `change`, `unbacked`, `dedicated`,
  `status` (the capability its status and receipt replay stay bound to, `refused` for the album) and, for a change
  kind, its payload class and display name. The registry sets, `prepare_change`'s isinstance dispatch, the broker's
  per-kind status rule, its dedicated-kind tuples, the generic artifact kinds of `send_prepared_artifact` and the
  change-policy allowlist read it. A payload may name `extra_capabilities` (a styled caption:
  `edit_own_styled_text`), checked with the kind's own status capability. The album stays dedicated with its own
  status model. The full isolated-HOME suite ran unchanged on the table commit before anything else was added.
- **Profiles.** `edit_own_caption` and `edit_own_styled_text` join `archive_edit` (every own-message edit; one
  profile unlocks a styled caption or a styled text edit). `pin_messages` and `delete_own_message` get the new
  profiles `pin` and `delete`, each depending on `send` only, so enabling edits never grants a broadcast pin or an
  irreversible delete. Rejected: a new `message_actions` profile for all four (enabling edits would grant delete);
  a separate `message_edits` profile depending on `archive_edit` (a second dependency level the one-level
  enable/disable rule does not express). Consequence, recorded: an owner who had `archive_edit` on sees it
  `partial` after the upgrade until enabling it again.
- **Caption input is refused, never rewritten.** `new_caption` must already be the stored form; edge whitespace
  has its own fixed detail, any other change under the shared normalization (NFKC, CR/CRLF, tab, U+2028, U+2029,
  U+030A, U+0333, U+033F) another, a control or format character the generic `invalid_input`. This deliberately
  differs from `prepare_text_edit`, which normalizes before the preview (owner decision 20.10.2026): caller style
  offsets address the caption as given, so a rewrite would move them.
- **Removal** is `new_caption=""`, sent as exactly the empty `formattedText` (never null); removing an absent
  caption is `unchanged_caption`. A plain caption equal to the current one but dropping formatting is a change.
- **Above-media flag.** The request carries the reviewed flag; for documents, audio and voice notes (no caption
  position, TDLib drops the flag) it is false, and the result check compares it only where the kind has one.
- **Styled conjunction.** A styled caption without `edit_own_styled_text` is the typed `capability_disabled`
  (`missing_capabilities: ["edit_own_styled_text"]`, `next_action: enable_capability`), before any provider read
  and without a draft, as albums do for `video_send`. A styled draft's apply, receipt replay and `get_send_status`
  stay bound to both edit capabilities (content-free `expired`/`outcome_unknown` otherwise), and the in-lock guard
  checks both.
- **Verification.** `applied` needs the same message of the same content kind, exactly the new caption, exactly
  the caller's styles, only fieldless auto-detected extras (Url, EmailAddress, PhoneNumber, Mention, Hashtag,
  Cashtag, BotCommand, BankCardNumber) on whole-scalar boundaries, the reviewed above-media flag where the kind has
  one and an `edit_date` not before the reviewed one (amended by review fix 057: touching pieces TDLib cut a span
  into are joined first, and a MediaTimestamp exactly on a whole timestamp token is tolerated; see below). Media
  identity is not compared again (the spec rule);
  a 4xx is `failed`, everything else after transport `outcome_unknown`. Corrected by review fix 057b: the pinned
  TDLib keeps a style span that covers only whitespace inside the text (`fix_formatted_text` removes only empty
  entities and trims the edges, which preparation refuses; TDLib's own test keeps Bold over the space between two
  emoji), so such an edit reads `applied` unless Telegram returns the span changed, as a formatted send does.
- **Seams left for parts 2 and 3.** Styled text edits: `prepare_text_edit` gains `outgoing_entities` gated by
  `edit_own_styled_text` (listed schema change), a second `editMessageText` shape, `TextEditSpec` styles with
  `extra_capabilities`, and the generic `edit_entities` field doc (it names no tool) for the new parameter. Pin and delete: new
  rows in `DRAFT_KINDS`, `CHANGE_REQUEST_TYPES`/allowlist entries (the exact-set test in
  `tests/test_caption_edit.py` lists what this part admits and must be extended deliberately), a `Delete` button
  (the renderer returns `change: bool` today; the delete dialog needs a third script), and the delete transport
  outside `_change_transport`'s "4xx proves no change" rule.

### Part 2 (styled text edit, pin and unpin) — lead decisions, owner review pending

- **Styled text edit.** `prepare_text_edit` takes an optional `outgoing_entities` (the five fieldless styles, the
  `prepare_text_send` span rules), gated by `edit_own_styled_text` with `edit_own_text`, `send` and `read`; listed
  schema change `0.57-styled-text-edit`. A styled draft is a `text_edit` draft whose `TextEditSpec.styles` names
  `extra_capabilities`, so the per-kind status rule, receipt replay, apply and the in-lock guard need both edit
  capabilities without a new kind. Without the style capability the result is the typed `capability_disabled`
  (`missing_capabilities: ["edit_own_styled_text"]`, `next_action: enable_capability`) before any read and without a
  draft, as for captions; `PrepareTextEditResponse` gains that status, `missing_capabilities` and `next_action`
  (both absent from every earlier dump).
- **Styled input is refused, never rewritten** (the caption rule): the spans address `new_text` as given. Edge
  whitespace keeps the existing fixed detail; any other normalization change gets the new fixed detail `styled new
  text changes under Telegram normalization (NFKC, line breaks, rewritten characters); send its stored form`; a
  control character or spans that do not fit are the generic `invalid_input`. The plain edit keeps the owner's
  20.10.2026 normalization. Rejected: normalizing styled text before freezing the spans, as `prepare_text_send`
  does (a rewrite would silently move the reviewed spans).
- **Plain edits stay byte-identical.** The preview's `outgoing_entities` is omitted when absent, so a plain
  preview, its digest, its request (`entities == []`) and its result rule (text, ids, `edit_date`; entities not
  compared, as in 0.52) are unchanged, and the broker calls the provider without `styles`. Restyling the same text
  is a styled change when the styles differ from the current non-auto-detected formatting; the same text with the
  same formatting is `unchanged_text`. Recorded: removing all formatting from an otherwise unchanged text is still
  not offered (the plain rule refuses equal text).
- **Second `editMessageText` shape.** The validator admits `entities` either empty (plain) or a non-empty list of
  canonical caller styles; the provider builds the styled shape only from styles passed by a styled draft and
  revalidates `TextEditSpec(snapshot, new_text, styles)` under the provider lock. Verification uses one shared rule
  (`edit_drafts.exact_styles`): exactly the caller's styles plus only fieldless auto-detected extras on whole
  scalars; the caption verifier now calls it too (no behaviour change, its tests unchanged). Review fix 057 amends
  the rule (joined pieces, media timestamps) and gives it to the formatted send; see below.
- **Pin evidence is the F14 projection.** The message may be anyone's, so prepare reveals it (hence `read`); it is
  projected and shown exactly like a forward source (`ForwardSourcePreview.from_source`, shared dialog lines
  `_message_lines`), and content that projection cannot show is refused (`unsupported_source_content`,
  `hidden_source_content`, `unsupported_source_state`), plus `not_pinnable` from `can_be_pinned`. Rejected: an
  id-only preview (the owner would approve a pin of a message nobody showed them).
- **Already in the target state.** At prepare (after the owner recheck, before `not_pinnable`) it is
  `already_pinned` / `not_pinned` without a draft; at apply the re-read returns the same statuses with no dialog
  and no attempt (the archive's `already_in_target` pattern).
- **Final state and 4xx read-back.** After `ok`, bounded `getMessage.is_pinned` reads (the archive observation:
  0.25 s, at most 10 s, 64 reads, each its own serialized call); `applied` only when the target state is observed,
  otherwise `outcome_unknown`. A 4xx proves the attempt changed nothing; one read-back under the same provider
  scope raises `ChangeRejectedInTarget` when the target state holds, reported as `already_pinned` / `not_pinned`
  with `is_pinned` and the provider code; otherwise, or when the read-back fails, `failed`. The receipt is `failed`
  with the evidence `provider_failed_already_pinned` / `provider_failed_not_pinned`, so a replay keeps the
  classification while `get_send_status` stays content-free. Rejected: treating a racing pin's 4xx as `applied`
  (this attempt did not change it) and plain `failed` (it hides the true final state).
- **Shapes and surface.** `pinChatMessage` with `disable_notification: true` and `only_for_self: false` fixed,
  `unpinChatMessage` with exact keys; both only through the change transport; bulk unpins unreachable. One kind
  `pin_change` (display name `Pin change`) for both actions; a pin and an unpin of one message supersede each
  other. `prepare_pin_change` is read-only stateful, `apply_prepared_pin_change` is `_TRANSFER` (not destructive:
  an unpin reverses a pin); the apply response carries the observed `is_pinned`. Census 60 → 62; both descriptions
  within 600 characters (total 33,877 of 34,200).
- **Dialog.** The pin dialog states that Telegram posts a visible service message every participant sees, that the
  pin is for everyone and silent, and that earlier pins stay pinned; the unpin dialog states that no service
  message is posted. Forum-topic pins and pins in private chats or Saved Messages follow Telegram's own rules and
  belong to the owner session.
- **Runtime text.** The `_manifest` `forbidden` list now names the authority as it is (one Main/Archive move, one
  text or caption edit of an own message, one pin or unpin), which also corrects its part 1 wording.
- **Skill budget.** The pin row and the styled-edit hint fit by removing three sentences the skill repeated
  elsewhere (`invalid_cursor` carries `restart_listing`, reading never marks messages read, an archived chat may
  return to Main) and by rewording; 19,998 bytes, 265 lines.
- **Seams left for part 3 (delete).** See the tasks file.

### Part 3 (deletion of one own message, dialog goldens, isolation) — lead decisions, owner review pending

- **Scope, as specified: one own message, for everyone, in v1.** The refusals run in a fixed order after the chat
  identity: Saved Messages (the account's own chat, where Telegram offers only a deletion for yourself) is
  `saved_messages`, a message that is not the account's outgoing message is `not_outgoing` (even where admin rights
  would let it delete another member's message), then the F14 projection's refusals, then
  `can_be_deleted_for_all_users` false is `not_deletable_for_all` (even when `can_be_deleted_only_for_self` holds).
  Rejected: an `only_self` option (permanent loss with no counterpart for the recipient; the spec's v1 decision).
- **The owner sees what is deleted: the F14 projection.** The message is projected, hashed and shown exactly like a
  forward source (`ForwardSourcePreview.from_source`, the shared `_message_lines`), so content the projection cannot
  show (service messages, stickers, polls, buttons, hidden entities, scheduled or sending messages) is refused with
  its code. An own forward is admitted; the dialog says it is a forward. Rejected: an id-only preview for
  unshowable content (an irreversible action nobody showed the owner).
- **Its own transport.** `deleteMessages` is in the allowlist and the change set (so `_call` refuses it in any shape)
  and in a new `_DELETE_REQUEST_TYPES`; the one raw exchange of the change transport is factored out
  (`_change_exchange`), `_change_transport` keeps its "4xx proves no change" rule for the archive, edits and pins and
  refuses a delete, and `_delete_transport` returns the raw answer for the caller to classify. Closed shape: exactly
  one ID in a list, `revoke` exactly true; several IDs, `revoke: false` and the history, by-sender, by-date, chat,
  Saved Messages topic and forum topic deletes stay unreachable (exact-set and negative tests).
- **The read `ok` needs.** Under the provider lock: the locked revalidation (chat, `getMessage`,
  `getMessageProperties`, account, equal to the reviewed snapshot), the guard, then one more `getMessage` of the exact
  message with the reviewed projection as the last request before the attempt (critic correction 1: TDLib answers
  `ok` without a server request for a message it does not hold). A failing or changed read is `local_failed` with no
  attempt.
- **Evidence order.** `ok` is `applied` (receipt `observed` = `deleted`; nothing is read afterwards, since a later
  `getMessage` answers 404 from TDLib's local deleted set). A 4xx gets exactly one `getMessage` read-back (TDLib
  refetches from the server after a failure): the exact message found is `failed` (detail with the code and "read back
  right after, the message is still in the chat"); a 404, another message, a malformed answer or a failed read-back
  is `outcome_unknown`. Every other error, a lost or late answer, a closed session and any result but exactly `ok` is
  `outcome_unknown` with no read-back. Rejected: the generic 4xx rule (TDLib already deleted the local copy);
  `updateDeleteMessages` or a post-`ok` 404 as evidence (both local); a read-back after a 5xx (the server may still
  have deleted it).
- **Restart replay disclosed.** TDLib logs a server deletion and replays it after a restart, so every unknown
  deletion says it may still complete later, even after a restart: the fresh `outcome_unknown`, its receipt replay,
  the lost-authority answer (`_change_attempted` takes the kind's unknown detail) and the proxy's lost-broker answer,
  each with `next_action: check_send_status`; `get_send_status` stays content-free. A deletion completed by that
  replay leaves nothing to prepare (a new prepare is `unavailable`), so it is never made twice.
- **Dialog.** `render_approval` returns a closed verb (`send`, `change`, `delete`) instead of a change flag; a third
  script from the same template carries the `Delete` button (`approve deletion`, `nothing is deleted.`), Cancel
  stays the default, and the send and change scripts keep their 0.54 bytes (hash-pinned). The document states that
  the deletion is irreversible, removes the message for every participant and unpins it if pinned. The pin
  statement is static, not the current pin state: the projection carries no pin state, and a static statement is
  always true without adding an apply-time refusal. Rejected for now: a typed confirmation (the map's suggestion);
  it needs a dialog model beyond the 0.54 renderer, and the native dialog's Cancel default, timer and named `Delete`
  button are the gate.
- **Surface.** `prepare_message_delete` is read-only stateful and carries no `next_action` (no status names a
  recovery condition, the pin's rule); `apply_prepared_message_delete` is destructive like the edits. Census 62 → 64;
  descriptions 454 and 598 characters (total 34,929 of 35,400); listed schema change `0.57-delete-tools`; the
  `_manifest` forbidden list names one approved deletion of one own message for everyone.
- **Dialog goldens (item 2)** for a styled caption edit, a styled text edit, a pin, an unpin and a deletion, each
  complete, with and without a registry (`tests/test_message_action_dialogs.py`).
- **Skill budget.** The deletion row and guidance fit by shortening three sentences the tool descriptions already
  carry (the receipt replay of a repeated call, the draft-tool coverage, the status tool's scope) and dropping "not
  decoded"; 19,993 bytes, 265 lines.
- **Recorded, not changed.** An own message deleted on another device for that account only, in the one round trip
  between the last `getMessage` and the request, makes TDLib answer `ok` without a server request: the result reads
  `applied` while other participants may still see the message. No client-side check can close that window. The
  real-provider behaviour behind the evidence order (local-first deletion, the not-held `ok`, the refetch, the
  logged replay) is modelled from the pinned C++ source in the fake, not observed; it belongs to the owner session.
- **Version not bumped:** it stays 0.56.0.dev0; the changelog paragraph is under that heading.

### Review fixes (057) — lead decisions, owner review pending

The 057a review's five confirmed findings and its contested one are fixed; details, tests and evidence are in the
[task record](0.57-own-message-actions-spec.tasks.md#review-fixes-057).

- **TDLib's split form is the edit.** The pinned TDLib returns a style cut into touching pieces at every style nested
  in it and at both ends of every auto-detected entity inside it (`split_entities`). The shared rule joins touching
  pieces of one style and compares the joined spans with the caller's exactly; overlapping pieces fail. Rejected:
  porting the cut points (TDLib also cuts at entities it then hides, such as a media timestamp past the duration).
- **The formatted send takes the same rule.** Its check had the same defect and refused every entity Telegram detects
  in the text; it now calls `exact_styles`.
- **Media timestamps tolerated exactly.** A MediaTimestamp is admitted only on exactly a whole timestamp token (a port
  of `find_media_timestamps`) with that token's value, and on a video, audio or voice note caption within the media's
  own duration; every kind can carry it, so none is refused by kind. Rejected: refusing timestamp-like tokens at
  prepare (it would block any text with a time such as 10:30). Recorded: such a message then cannot be edited again
  with these tools (source content keeps MediaTimestamp closed).
- **One dialog per draft.** Every send and apply reserves its draft from just before the owner dialog until its claim,
  releasing an unclaimed reservation when the call ends; a concurrent call answers `dialog_unavailable` with no
  dialog. This replaces the recorded 0.54 limit (both callers saw a dialog, the loser read `outcome_unknown`); a call
  arriving after the claim still reads `outcome_unknown` while the attempt runs. Rejected: holding the dialog lock
  until the claim; deletion only.
- **Skill and reference.** An unknown deletion is never reported as deleted (a read cannot confirm it); five general
  reference passages corrected.
- **Recorded for a follow-up.** Plain reply and topic text sends still require an observed message without entities,
  so one containing a link, mention or hashtag reads `outcome_unknown`; it predates 0.57.
