# 0.52 QR-first onboarding — implementation spec

**Status:** accepted 14.10.2026
**Branch:** `qr-onboarding-052`
**Tasks:** [`0.52-qr-onboarding-spec.tasks.md`](0.52-qr-onboarding-spec.tasks.md)
**Requirement:** [0.52 QR-first onboarding](0.52-qr-onboarding.md) (QR-01…QR-06). This spec
implements that requirement; where they disagree, the requirement wins and this spec is
amended in a separate commit.

---

## 1. One sentence

On a clean macOS user, an MCP client (Claude Code or Codex) installs the bundle, runs
`telegram-search-setup connect`, the owner scans a QR on a local browser page with their
phone (plus 2FA if set), and the same client then completes a bounded own-chat search —
with no API ID/hash entry, no manual config edits and no secret visible to the model.

## 2. Input → output

| | what | format |
|---|---|---|
| input (build) | Product API identity: the owner's existing api_id/api_hash, read from the build machine's Keychain behind an explicit assembly flag | Keychain records `api_id`, `api_hash` under the existing service |
| input (runtime) | QR scan + confirmation on phone; optional 2FA password typed into the local page | human action; password as HTTP POST body to loopback only |
| output | Managed encrypted session, Ready broker, MCP + both skills registered in Claude Code and Codex | existing enrollment/receipts + new fields below |

**New data:**

- `app-identity.json` inside the installed runtime (owner-only, read-only, bundle-hashed):
  `{"version":1,"api_id":int,"api_hash":"<32 hex>"}`. Absent in source builds.
  Distributed client parameters are extractable by design; this is accepted (requirement,
  "Owner inputs").
- `enrollment.json` gains `credential_source: "keychain" | "bundled"` and
  `identity_fingerprint: sha256("<api_id>:<api_hash>")`. Records without these fields are
  read as `keychain` with fingerprint computed on first use (backward compatible; no
  rewrite of existing records unless a state change already writes the record).
- `run/connect-status.json` (0600, no secrets): `{"phase", "code", "updated_at",
  "expires_at"}`. Phases: `starting | waiting_for_scan | waiting_for_password | authorizing
  | handing_off | ready | failed | expired | cancelled`.
- Install receipts gain a Claude Code registration record and `~/.claude/skills/*` skill
  receipts, mirroring the existing Codex/`~/.agents/skills` receipts.

**Credential resolution (setup, connect and broker use one function):**
1. Enrollment exists → use its `credential_source`; if the resolved pair's fingerprint
   differs from `identity_fingerprint`, refuse `identity_changed` (never re-bind silently).
2. New enrollment: both Keychain records present and valid → `keychain` (owner override and
   existing users). Otherwise `app-identity.json` present → `bundled`. Otherwise `connect`
   refuses `app_identity_missing`; the legacy Terminal `setup` keeps prompting for the pair.
3. Partial Keychain state (one record) → `connect` refuses `credential_conflict`. The
   Terminal `setup` path keeps its pre-0.52 add-only partial-pair resume and uses the
   bundled identity only when no Keychain record exists (amended 16.10.2026).
4. A pre-0.52 record gains its binding on its next state write (setup resume or connect);
   for a bound record the Terminal path checks a typed pair against the fingerprint
   before any Keychain write (amended 16.10.2026).

Owner override: new closed command `telegram-search-setup api-credentials` (native Terminal
only, hidden prompts, add-only — reuses `_api_credentials`). Must run before first `connect`.

## 3. Scenario

Agent side (captured, no secrets):

```
<install bundle as today>                      → activation_required, now pointing at connect
telegram-search-setup connect                  → {"status":"screen_opened"}  (returns at once)
telegram-search-setup wait                     → blocks ≤ 540 s, returns current phase; repeat
                                                 until ready | failed | expired | cancelled
<client reconnect> _manifest(check_broker=true) → compatible
<one bounded own-chat search>
```

Human side: a browser tab opens by itself at `http://127.0.0.1:<port>/#t=<token>` with a QR,
"Open Telegram on your phone → Settings → Devices → Link Desktop Device", a live countdown,
then the 2FA field if needed, then "Connected — return to your assistant".

**Process model.** `connect` validates the installation and starts a transient launchd job
`com.<home>.telegram-search-mcp.connect` (outside the agent's process tree and sandbox),
then returns. The job runs the connect helper: takes the owner lease, resolves credentials,
creates/reuses the managed enrollment, starts the loopback server, opens the default
browser through `osascript -` with the URL on stdin (so the token never appears in any argv or passes through the agent), drives TDLib,
tears the auth client down, hands off to the broker via the existing `handoff_broker`, writes
the final phase and boots itself out. If launchd submission fails: `connect_launch_failed`
with `next_action: run_connect_in_native_terminal` (running `connect` from native Terminal
runs the helper inline).

**Auth loop** (extends `run_setup`'s structure, separate entry point; Terminal path unchanged):
- `WaitTdlibParameters` / `WaitEncryptionKey` → as today, with resolved credentials.
- `WaitPhoneNumber` → `requestQrCodeAuthentication(other_user_ids=[])` once.
- `WaitOtherDeviceConfirmation(link)` → validate link (`tg://login?token=` + base64url,
  ≤ 256 bytes), render QR SVG server-side, publish; each new link replaces the QR. Waiting
  compares link value, not just state type.
- `WaitPassword(hint)` → show sanitized hint (≤ 128 chars, rendered as text). One request
  in flight; definitive `invalid_password` allows re-entry up to 5 times per helper run
  (UX bound; Telegram's own flood control is the security bound). Timeout/transport error
  → uncertain → stop with resumable failure, never resubmit.
- `Ready` → teardown + handoff as today. An observed Ready wins over a cancel pressed in
  the same slice: the device is already authorized, so the run reports it truthfully.
- A password is not submitted with less than 5 s of lifetime left (its outcome would be
  uncertain by construction); the run expires instead. Any non-definitive password
  outcome, including a malformed provider response, is `password_submission_uncertain`. `WaitCode` or any other state → `unsupported_auth_state`
  with `next_action: use_terminal_setup_fallback`.
- Whole helper lifetime 600 s, then `expired`, auth client torn down, server closed.

**Loopback server** (stdlib `ThreadingHTTPServer`, bind `127.0.0.1:0`):
- 32-byte random token in the URL fragment; JS sends it as `Authorization: Bearer`.
  Fragment is never sent in requests or referrers.
- Every request: `Host` must equal `127.0.0.1:<port>` (DNS-rebinding guard). POST: `Origin`
  must equal `http://127.0.0.1:<port>`; JSON body ≤ 4 KiB.
- Endpoints: `GET /`, `GET /app.js`, `GET /app.css`, `GET /api/state`, `POST /api/password`,
  `POST /api/cancel`. Nothing else; no CORS headers.
- Headers: CSP `default-src 'none'; script-src 'self'; style-src 'self'; img-src data:;
  connect-src 'self'; frame-ancestors 'none'`, `Cache-Control: no-store`,
  `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`.
- No request logging (override `log_message`). QR link and password never reach stdout,
  stderr, status file or exceptions.
- UI strings in Russian and English, chosen by `navigator.language` (`ru*` → Russian).
- QR encoder: `segno` (pure Python, BSD-3), pinned and added to the bundle and notices.

**Reconnect (QR-06).** When the exact receipt-bound broker answers a compatible handshake
but its check reports authorization not ready, `connect` (and only `connect`) may stop that
one broker via `launch_agent`, run the QR flow on the existing managed enrollment and key,
and hand off again. This is a deliberate, narrow exception to "never stop a competing
owner": a foreign, incompatible or Ready owner is still never stopped.

**Registration.** Installer adds, with ownership receipts and rollback:
- Codex: unchanged `mcp_servers.telegram_search`.
- Claude Code: `claude mcp add-json --scope user telegram_search {...}` via the `claude` CLI
  found at a fixed list of paths. State is read from the user-scope `mcpServers` object of
  `~/.claude.json` (never `claude mcp get`); a different existing entry refuses the install as
  `claude_registration_conflict`; a missing CLI records `claude_code: not_found` (not a failure).
- Skills: `telegram-search` and `telegram-setup` into `~/.agents/skills`, and into
  `~/.claude/skills` only when `~/.claude` exists or the CLI was found (else
  `claude_skills: skipped`), refusing foreign directories.
- `telegram-setup` SKILL.md rewritten for the connect/wait flow; it never asks for secrets.

## 5. Out of scope

- Migrating the owner's existing 0.51 installation to 0.52 (separate slice).
- Claude Desktop registration; claude.ai web/cloud (no HTTP transport, F19).
- Multiple accounts (F16), sending features, reader changes.
- Public hosting, publisher trust/signing, source/notice closure beyond adding `segno`.
- Legal sign-off on Telegram API terms §1.5 (recorded as a risk, not resolved here).
- Changing the phone/code Terminal path beyond credential resolution.

## 7. Who decides

Deterministic: state machine, credential resolution, server guards, registration receipts,
status phases. Human: QR scan, phone confirmation, 2FA, judging page clarity (criterion 6),
accepting real-run evidence. Sequential: phases A→F all touch the owner lease/enrollment/
installer; no parallel writers. A blind review subagent may run read-only in parallel.

## 8. Risks and degradation

- **Shared api_id on the owner's main number.** A §4 cut-off (e.g. over the §1.5 AI clause)
  would stop every bundled-identity user *and* the owner's own installation. Mitigation: the
  `keychain` override path; documented in install.md. Accepted by the owner on 2026-10-14.
- Launchd job blocked from the agent sandbox → explicit `connect_launch_failed` + Terminal
  fallback; never silently run inside the sandbox.
- Browser cannot open (headless/SSH) → status stays `waiting_for_scan`; `wait` returns
  `next_action: scan_qr_on_this_mac_screen`; the setup skill asks the user whether the page is
  visible and otherwise uses the Terminal fallback; the URL is never printed (amended 16.10.2026).
- Uncertain auth submission or teardown → existing resumable failures (`auth_destroy_failed`
  keeps the lease until process exit). No retries of uncertain steps.
- Existing session present → never overwritten; `legacy_unmanaged` refusal unchanged.

**Ceiling:** phases A–F, each closed by its gate (tasks file). Three distinct failed
hypotheses within one phase → stop and report with the stop log.

**Amendments 16.10.2026 (integration review):**
- A refused `bootstrap-install` prints `{"status":"refused","code":<code>}` with the
  installer's fixed code when it is in the installer's closed set, else
  `bundle_admission_or_install_failed`; other launcher actions refuse `bundle_admission_failed`.
- `connect`'s broker probe: handshake ≤ 3 s, then `check` ≤ 25 s for a compatible broker. A check
  that runs out on an enrolled broker passing read-only validation is
  `broker_starting` / `wait_then_connect_again` (never stopped); a broker failing validation or
  the handshake is `owner_busy`. `connect` returns within 40 s in that case (10 s otherwise).
- A launch (`Selection.check`) no longer reads the Codex `config.toml` or the
  `~/.agents/skills` copies; release tree, index, receipt, pointer, journal and home binding
  stay checked. The installer still verifies client registrations and skill copies at
  install/repeat time.
- `run/connect-status.json` gains `retry_after` (int 1..86400, only with `flood_wait`, else
  null); the key is always written and read strictly. `wait` and the inline result carry it
  for `flood_wait`, the page shows the wait in minutes, `next_action` is
  `wait_retry_after_then_connect_again`.
- One `next_action` table in `connect_flow` serves `ConnectResult`, `wait`, the inline result and
  CLI refusals and covers every produced code; non-terminal phases map to `wait`,
  `tell_user_to_scan_qr_then_wait` and `tell_user_to_enter_password_on_page_then_wait`.
- An OS-refused write (sandbox) creating the run directory, `connect.lock` or removing the
  status before launchd is tried is `connect_launch_failed` (`owner_unsafe` in native Terminal).
- `helper_exited` → `run_connect_in_native_terminal`. A helper failing before or around
  `run_connect` (server start, UI, a raising run) writes a terminal status unless one exists.
- `wait` returns at the first phase different from the one seen when it started (absent =
  `starting`), at a terminal phase or at 540 s; `scan_qr_on_this_mac_screen` only when
  `waiting_for_scan` outlasts a whole `wait`.
- New agent-safe command `cancel`: boots out our own busy connect job (`cancelled`) or reports
  `nothing_to_cancel`; launchctl failure is `cancel_failed` / `wait`. The launchd helper's
  SIGTERM handler requests cancel through the UI so `run_connect` tears down normally, and skips
  the linger. A helper killed without a terminal status gets `cancelled` and a quiet broker restore.
- `run_connect` also expires when the wall clock passes the status `expires_at`; the helper takes
  one deadline and passes it as `expires_at` (lifetime = deadline − now). `HUNG_GRACE` is 120 s.
- `already_connected` removes a stale status when no helper holds `connect.lock`.
- The bundle assembler refuses `payload_app_mismatch` unless `app/telegram_search_mcp/` equals the
  checkout's package (.py set and sha256) and `app/segno/__init__.py` exists.
