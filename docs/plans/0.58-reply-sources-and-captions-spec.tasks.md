## Part 1 — freeze and ladder table (work items 1 and 2)

**Freeze.** `tests/reply_ladder_matrix.py` generated `tests/fixtures/reply_ladder_matrix_0_57.json` once at the
0.57 tip (f2239c4), before any production change. `tests/test_reply_ladder_matrix.py` pins it by sha256 and
compares freshly computed rows byte for byte. The 6,098 rows cover:
- every subset of the eight span families × {text, document, photo, voice note} × the datetime levels (absent,
  plain, relative, absolute, all three);
- sanitizer-rewritten bodies and forum-topic sources;
- CustomEmoji and MediaTimestamp probes, all refused at 0.57;
- the inline v23 TextUrl literals;
- every row of the eight existing reply goldens.

Each row records the version, the capability tuple, `is_media`, `sanitized`, sha256 digests cut to 16 hex
digits of the projection, the display and one fixed text-reply preview, and every forged version in 0..31 that
the stored projection would also accept (none).

**Ladder table.** `src/telegram_search_mcp/reply_source_ladder.py` is the one owner of each family's name,
keyword, capability, entity map, rank, text and media version, overlap exclusivity and inert display, and of
the fixed capability listing order. Version selection, presence, capability tuples, stored-version admission and
the shims' keyword admission all derive from it. The keyword signatures of `formatted_text`, `validate_content`,
`render_formatted_text`, `render_content` and the media `media_content`, `validate_content` and `render_content`
stay as shims over new `*_for(…, admission)` functions. `_boundaries` and `_inert_json_string` stay in
`reply_formatted_sources`.

**Gate.** The full isolated-HOME suite at 85ef050 gave 4118 passed, 0 failed, 0 skipped, 20830 subtests passed in
2216.07s. That is the 0.57 baseline of 4106 plus the 2 matrix and 10 ladder tests.

Lead decisions, owner review pending:
- **Refusals are not frozen by message.** A refused input records only nulls, because refusal messages are
  internal and the broker maps them all to `unavailable`. The media "disagrees" messages merged into one.
- **The stored-version check replaces the per-family caption checks.** A stored media projection validates under
  its top family and every family below it, and its validated caption must select the stored version. This
  replaces the seven per-family checks and the v12/v14 special cases. The keyword shims keep their 0.57 rule:
  each flagged family must be present.
- **The datetime levels are table rows.** Relative and Absolute are rows that refine DateTime by formatting type.
  They share `reply_datetime_targets` and are absent from the listing order.
- **Exclusivity and inert display are table fields.** They are per-family policy, so a new family sets them in
  its row.
- **The media display fails closed on an inert family.** It refuses until it gets the whole-record inert path,
  so giving TextUrl a media version cannot silently sanitize hidden URLs. This is unreachable at 0.57.
- **The preview digest is the text-reply digest only.** The reply-artifact facts move to v2 in part 3, which
  would otherwise change a frozen value that has nothing to do with the ladder.

Seams for parts 2 and 3:
- A new family is a `Family` row: a rank above TextUrl, `text_version` or `media_version` set to `None` where
  the family is refused, placed at the front of `LISTING_ORDER`, and `exclusive=True`. v27 stays refused because
  no row claims it.
- Media TextUrl (v24) means setting `TEXT_URL.media_version` and replacing the fail-closed branch of
  `reply_media_sources._render` with the inert record.
- Flipped 0.57 probes go into `FLIPS` in `tests/test_reply_ladder_matrix.py`, each with its reason. A flip may only
  admit an input that 0.57 refused, and every other row must stay byte-identical. `SPANS` in
  `tests/test_reply_source_ladder.py` needs a builder for each new family.
- Part 3 (formatted captions) does not depend on the ladder. Its reply-artifact preview change sits outside the
  frozen matrix.

## Part 2 — new families on the ladder table (work items 3–6 and 9)

**Families.** Three ladder rows, each exclusive and without a 0.57 shim keyword:
- **v24, media TextUrl.** `TEXT_URL.media_version = 24`. A caption with an inert family renders the whole media
  record (caption and media facts) through v23's one inert JSON layer; part 1's fail-closed branch is gone.
- **v25/v26, CustomEmoji** (`reply_custom_emoji_targets`). The id is TDLib's decimal int64 string, 1 to 2^63−1; an
  integer, sign, padding or non-ASCII digit refuses. The covered text is exactly one emoji. The record shows
  `custom_emoji_id`.
- **v28, MediaTimestamp** (`reply_media_timestamp_targets`), captions only, so v27 is reserved. The entity sits on
  one whole timestamp token with that token's value, from 0 to the media's own duration. Only a voice note has a
  duration, so text, documents and photos refuse it.

**Capability order.** `LISTING_ORDER` now starts with media timestamp, custom emoji, then TextUrl, so every
v1–v23 tuple is unchanged. Both capabilities are in `KNOWN_CAPABILITIES` and the `replies` profile only.

**Unchanged surfaces.** Forward and own-message edit admission still refuse CustomEmoji and MediaTimestamp. The
TDLib allowlist equals the 0.57 set exactly, without `getCustomEmojiStickers`. Both are pinned in
`tests/test_reply_families_058.py`, which also runs the production broker over the synthetic transport for one
text and two artifact replies.

**Flips (criterion 4).** 1,926 media TextUrl rows (subset, sanitizer-rewritten and topic sources on documents,
photos and voice notes), the eight decimal-string custom emoji probes and the two voice-note timestamp probes.
Integer ids, timestamps beyond the duration and timestamps outside a voice note stay refused. Six 0.57 test cases
that asserted a TextUrl caption refuses now assert v24; a seventh now keeps a caption past the display bound closed.

**Gate.** The full isolated-HOME suite at df4db2c gave 4142 passed, 0 failed, 0 skipped, 22792 subtests passed in
1787.42s: part 1's 4118 plus the 24 tests of `tests/test_reply_families_058.py`. The follow-up 1e0ec05 only drops
an unused import and fixes a docstring; its two files pass again (26 passed).

Lead decisions, owner review pending:
- **Profile placement.** Both capabilities join `replies`, the profile that already holds every
  `reply_*_targets` and depends on `send`. They are reply conjuncts, not operation gates.
- **The schema fingerprint moves.** `CapabilityName` enumerates `KNOWN_CAPABILITIES` in eleven output schemas, so
  the critic's "new capabilities do not change it" was wrong. The change is listed as
  `0.58-reply-family-capabilities` and the pin moved; a pinned policy needs the installer's rewrite, as in 0.57.
- **Criterion 4 is read together with work item 4.** The custom emoji probes with a decimal-string id over one
  emoji flip to v25/v26, because work item 4 admits exactly that shape. Only integer ids stay refused.
- **A timestamp must match its token.** TDLib creates these entities from the caption text, so the value is
  checked against the 0.57 grammar of TDLib's `find_media_timestamps` as well as the 0–duration range.
- **The duration bound is a parser argument, not a table field.** It comes from the media itself, mirroring
  TDLib's missing duration (-1) for documents and photos.
- **One emoji is a closed local grammar.** One element (a pictograph with at most one skin-tone modifier, a lone
  modifier, a keycap or a two-letter flag) plus at most one trailing VS16. ZWJ and tag sequences never arrive,
  because the visible-text policy refuses their format characters. During development every one of the 2,331
  control-free elements of the pinned TDLib emoji table (`tdutils/td/utils/emoji.cpp`) was admitted; the table is
  not vendored.
- **Custom emoji are not inert.** The id is ASCII digits and the covered emoji goes through the sanitizer. Heavy
  messages hit the 4,096 display bound: at most 27 custom emoji with 19-digit ids in a text, 26 in a caption,
  disclosed in `docs/reference.md`.
- **The inert media record reports `sanitized` for every media string.** A document or voice note with a TextUrl
  therefore always reports it, because `/` in the MIME type is escaped.
- **Budgets.** The shared reply description was shortened to keep the 0.54 total; the skill's reply paragraph was
  compacted to 19,994 bytes.

Seams for part 3:
- Formatted captions (work item 7) do not touch the ladder files. `outgoing_entities` on the artifact and
  reply-artifact requests is another listed schema change: add its fixture and move the pin and
  `SCHEMA_CHANGES_SINCE_055` in `tests/test_account_registrations.py` again.
- The dialog (work item 8, criterion 6) still prints `reply_target.text` verbatim. Structured rows per hidden
  payload (`provider_url`, `custom_emoji_id`, `media_timestamp`) can be derived from the stored projection with no
  new `ReplyTarget` field.
- The reply-artifact preview v2 stays outside the frozen matrix, whose preview digest covers the text reply only.
- The owner session (criterion 8) needs a voice note at least three seconds long for the "0:03" caption.

## Part 3 — formatted captions, dialog, surface (work items 7 and 8)

**The defect older than 0.58 (first).** `send_observations._artifact_matches` required a sent caption's entities to
be `[]`, so an artifact reply whose caption held a link, mention or hashtag never confirmed and stayed
`outcome_unknown`. Every caption is now read back by its digest and `edit_drafts.exact_styles`: exactly the frozen
styles (none for a plain caption), joined from TDLib's split pieces, plus only the auto-detected entities. A media
timestamp is bounded by a voice note's own duration, is not compared on a video (the provider may re-encode it) or
on a document or photo reply (the replied media is not carried), and refuses on a document or photo without a reply,
where TDLib keeps none. Plain document, photo, voice-note and video sends register the caption digest too, so a
caption that comes back changed is no longer reported `sent`; only an artifact reply also binds its media shape.
`tests/test_caption_observations_058.py` failed on 91 checks before the fix. Fixtures in `test_tdjson.py` and
`test_video_send.py` that returned caption-less final messages now carry the caption that was sent; the 0.56 test
that refused a video caption digest now refuses only a malformed one.

**Formatted captions (work item 7).**
- **Gate.** `formatted_caption_send` is in `KNOWN_CAPABILITIES`, `SEND_DEPENDENT_CAPABILITIES` (so
  `required_capabilities('formatted_caption_send')` is `('formatted_caption_send', 'send')`) and the `send` profile;
  it is never an operation gate. The broker asks `send` and then it, from `required_capabilities()`; a reply asks
  `reply_artifact_send`, `send`, then it, before Telegram is read.
- **Requests.** `outgoing_entities` on `prepare_artifact_send`, `prepare_reply_artifact_send`,
  `update_reply_artifact_draft` and `prepare_video_send`; `update_draft` already had the field and now admits it with
  `caption`. The styles must address a caption already in its stored form (`caption_edit_drafts.normalized_caption`
  leaves it unchanged); anything else is refused, never rewritten. Listed as `0.58-formatted-captions`: 13 tools
  change structurally (the four requests, the video and artifact previews, and `formatted_caption_send` in the
  closed `missing_capabilities` enum) and `update_draft` in its descriptions; `SCHEMA_FINGERPRINT` and
  `SCHEMA_CHANGES_SINCE_055` moved.
- **Previews.** `draft_models.artifact_preview_digest`: domain `telegram-search-mcp.artifact` version 1 over every
  shown fact, the caption with its native styles and the fixed request shape. `prepare_artifact_send` and `get_draft`
  show `outgoing_entities` and `preview_sha256` only for a styled caption. Reply-artifact facts move to v2 for a
  styled caption and fill the `outgoing_entities` slot; video preview facts move to v2 the same way. Plain drafts,
  replies and videos keep their wire and digests (the pinned 0.53 reply-artifact digest test stays green).
- **Transport.** `tdjson._plain_caption(..., styled=True)` admits canonical frozen caller styles over a stored-form
  caption on a single `sendMessage`; album items keep `styled=False`. `send_document_message`, `send_photo_message`,
  `send_voice_note_message`, `send_video_message` and `send_reply_artifact_message` take the frozen styles,
  revalidate them against the caption, and (plain sends) the reviewed account and recipient title under the
  serialized provider lock, like formatted text; registration carries the styles with the caption digest.
- **Authority.** A styled draft is bound to the provider and epoch it was prepared under (the formatted-text
  fields); claim, prewire (`formatting_claim_current`), status and receipt replay check them and the capability.

**Dialog (work item 8).** A styled caption lists `Caption styles (exact caption; UTF-16 code units):` with each
style's covered text, and a styled file send shows its preview digest. A reply lists `Target styles and hidden
payloads` with one row per stored target entity: type, offsets, exact covered source text and its hidden payload
(`hidden URL`, `custom emoji id`, `media timestamp`, `mentions`, `unix time` with formatting, `language`). The rows
come from the stored projection, which the broker now passes as `reply_source`; the renderer refuses unless it
renders exactly the reviewed target. `ReplyTarget` gains no field.

**Surface and docs.** Tool descriptions stay within the 0.54 budget (35,396 of 35,400 characters; the shared reply
text was shortened); a new field description for caption styles and one for `update_draft`. Both search-skill copies
name `formatted_caption_send` (19,997 bytes, 264 lines). `docs/install.md` lists it in the `send` profile row and
the capability table; `docs/reference.md` gains "Styled outgoing captions (0.58 candidate)" and the dialog rows;
`docs/security.md` gains the hidden-payload rows and the styled-caption boundary; `CHANGELOG.md` a 0.58 paragraph
under the unreleased section. The launcher's profile names and the setup skills, which name profiles only, are
unchanged.

**Gate.** (Filled below.)

Lead decisions, owner review pending:
- **A styled caption must already be its stored form.** prepare_text_send lets styles address the normalized text;
  a caption is silently stripped of control characters by the 0.57 normalization, which could shift a span, so a
  styled caption follows the 0.57 caption edit instead: refused, never rewritten. Plain captions keep 0.57's rule.
- **Video captions are in scope.** The spec scopes styles to video captions too, and the critic found the
  `inputMessageVideo` guard; `prepare_video_send` gains `outgoing_entities` in the same listed change.
- **Version 2 only for a styled caption.** Reply-artifact and video facts stay version 1 for a plain caption, as
  reply text keeps v1 without styles, so no existing digest moves.
- **A styled reply's inner draft keeps its artifact digest.** `ReplyArtifactDraftPreview.draft` is a
  `DraftPreview`, whose styled form requires its own digest; the outer reply digest binds it with the target.
- **The read-back of a plain send checks the caption, not the media shape.** Correlation still decides a plain
  send's media, as since 0.5x; only an artifact reply binds the complete shape, as before.
- **A refusal of the gate keeps each tool's closed status.** `prepare_artifact_send` answers `error` and
  `prepare_video_send` `unavailable` (neither has `missing_capabilities`); the reply tools name it.
- **The dialog takes the stored projection as one more argument.** It is bound by rendering the reviewed target
  exactly, so the rows add evidence without a new `ReplyTarget` field or a new digest input.
- **A styled caption's receipt is disclosed like formatted text's:** only to the same current account, client and
  enabled policy.

Seams and limits:
- One approved formatted-caption send with real read-back is part of the owner session (criterion 8).
- Album item captions stay plain; a later spec may admit styles there.
