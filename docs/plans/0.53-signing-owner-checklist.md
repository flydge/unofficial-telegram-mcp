# 0.53 — signing and notarization: owner checklist

**For:** the owner, once, on the build Mac (CLIENTS-6). Everything here is personal to the owner's Apple
Developer account; nothing in this list is done by an agent.
**Spec:** [`0.53-client-distribution-spec.md`](0.53-client-distribution-spec.md), phase C.

Signing runs locally on this Mac (a CI with an exported `.p12` was rejected). The only credential the
release scripts ever name is a notarytool **keychain profile name**. No password, API key, Apple ID or
certificate leaves the login Keychain, and none is ever typed into a command line, an environment
variable, a log or the repository.

## 1. Developer ID Application certificate

1. Use an Apple Developer Program membership in which you may create Developer ID certificates (the
   Account Holder role, or an Admin with that permission).
2. Create the certificate on this Mac, so that its private key is generated in the login Keychain:
   - Xcode > Settings > Accounts > your team > Manage Certificates > `+` > **Developer ID Application**; or
   - Keychain Access > Certificate Assistant > Request a Certificate From a Certificate Authority (saved to
     disk), upload the request at developer.apple.com > Certificates > `+` > Developer ID Application, then
     open the downloaded `.cer`.
3. Never export the identity as a `.p12`, and never copy the private key to another machine.
4. Check: `security find-identity -v -p codesigning` lists exactly one
   `Developer ID Application: <name> (<TEAMID>)`. While a renewed certificate overlaps the old one, remove
   the old identity from the login Keychain first, or the preflight reports `identity_ambiguous`.

## 2. Notary credentials as a keychain profile

Choose a profile name, for example `tgmcp-notary`. It is not a secret.

- **App-specific password.** Create one at account.apple.com > Sign-In and Security > App-Specific
  Passwords. Then run `xcrun notarytool store-credentials` with no arguments and answer its prompts:
  the profile name, your Apple ID, the Team ID and the password, which is typed at the hidden prompt.
  Never use `--password`.
- **App Store Connect API key** (instead of the password). Create a Team key with the Developer role at
  App Store Connect > Users and Access > Integrations, download the `.p8` once, and run
  `xcrun notarytool store-credentials tgmcp-notary --key <path to the .p8> --key-id <key id> --issuer <issuer id>`.
  The key ID and issuer ID are identifiers, not secrets. Delete the `.p8` file afterwards: the key now
  lives in the login Keychain.

## 3. Preflight

```bash
packaging/signing_preflight.sh --profile tgmcp-notary            # add --team-id <TEAMID> to pick one team
```

It exits 0 and prints only `{"schema_version":1,"identity":"Developer ID Application: <name> (<TEAMID>)",
"identity_form":"common_name","team_id":"<TEAMID>","notary":"ok"}`: the certificate's common name, its
Team ID and whether `xcrun notarytool history` answers for the profile. It prints no submission or tool
output. `--team-id` filters first, so another team's identity never blocks yours. If your common name
falls outside printable ASCII (an accented name, for example) or holds quotes or shell characters, the
name is never printed: `identity` is then the certificate's SHA-1 and `identity_form` is `sha1`; pass
that SHA-1 as `--identity` below (the release build, the seed build and `notarize_release.sh` all
accept it). A refusal prints one fixed code: `usage`, `identity_unavailable`, `identity_missing`,
`identity_ambiguous` or `notary_profile_unavailable`.

Give the Team ID to the lead; it is recorded in the spec's decision table and becomes the Team ID pin of
the native lock, the manifest publisher and `release-pins.json`.

## 4. Application identity in the bundle (CLIENTS-16)

The bundle can carry an `app-identity.json` (an `api_id`/`api_hash` pair). A public release makes the pair
trivially harvestable, and a Telegram restriction under the API terms would stop every bundled install, and
your own installation too if it shares the pair. The release build therefore defaults to **no** identity.

If you decide to ship one, use a dedicated product pair, never your personal one, stored in its own
Keychain service:

```bash
security add-generic-password -s <service> -a api_id -w        # -w last: prompts for the value
security add-generic-password -s <service> -a api_hash -w
```

and pass `--app-identity-service <service>` to the release build. Only the identity file's sha256 is recorded
in provenance; the service name and the values appear in no log, receipt or output.

## 5. The signed release build

From a clean checkout at the release tag, first the ad hoc dry run (every step except notarization and
stapling: the payload zip is built, every Mach-O in the kit is checked to be ad hoc signed, and the DMG
is signed ad hoc and verified):

```bash
PYTHONPATH=src python3 packaging/release_build.py build --dry-run --offline --output <fresh dir> \
    --native-directory <prepare_native output> --cache <private download cache>
```

then the signed build and its check:

```bash
PYTHONPATH=src python3 packaging/release_build.py build --output <fresh dir> \
    --native-directory <prepare_native output> --cache <private download cache> --tag v0.53.0 \
    --identity "Developer ID Application: <name> (<TEAMID>)" --team-id <TEAMID> --notary-profile tgmcp-notary
PYTHONPATH=src python3 packaging/release_build.py check --output <same dir>
```

`--identity` may be the SHA-1 from the preflight instead of the name. In this mode the build:

- signs the bootstrap seed with the same identity (`build_bootstrap_seed.sh --sign-identity <identity>
  --team-id <TEAMID>`, identifier `<CODESIGN_ID_PREFIX>.bootstrap-verifier`, hardened runtime, secure
  timestamp); a seed that comes out ad hoc stops the build with `seed_unsigned`;
- before anything is notarized, checks every Mach-O the kit ships (the seed, and each payload file that
  `release.tar.gz` holds, matched to its index sha256) for the Developer ID designated requirement with
  your Team ID, a secure timestamp and the hardened runtime, or stops with `signature_refused`;
- renders `Install.command` with your Team ID, so `bootstrap.sh` gets `--seed-team <TEAMID>` and refuses
  any seed that is unsigned, ad hoc or another team's (`seed_signature_invalid`) before running it;
- signs the DMG, verifies it against the same Team ID requirement before submitting it and again after
  stapling, and only then asks `spctl`.

The three natives are re-signed with Developer ID here; the ad hoc dry run keeps their pinned unsigned
bytes, so they show no hardened-runtime flag there. Provenance records which (`native_signing`).

The quarantine on the staged seed is kept on purpose: Gatekeeper evaluates the notarized seed when
`bootstrap.sh` runs it. A bare Mach-O cannot be stapled, so on the first run after a browser download the
seed's notarization ticket is fetched online; an offline first run of a quarantined seed can be refused.

The output directory must be new, outside the checkout and outside `/tmp`. The build re-signs a scratch
copy of the interpreter with each candidate entitlement set and runs the probes: if the committed
`packaging/entitlements/python3.plist` (empty) is not the smallest passing set for your identity, it stops
with `entitlements_unproven`, and `work/entitlement-matrix.json` shows the table. The plist changes only
after review, and never to include `com.apple.security.cs.allow-dyld-environment-variables`.

The broker-under-launchd and connect-helper probes need your GUI launchd domain; run them in the owner
session (clean macOS user run, spec phase G), not in the build.

## 6. Plugin pins

When the Claude Code plugin's `release-pins.json` is switched to `"publication": "published"`, its
`team_id` must be your Team ID: `bin/install` refuses published pins with an empty one (`pins_invalid`)
and always passes `--seed-team`. curl sets no quarantine, so for the plugin path the Team ID check in
`bootstrap.sh`, on top of the sha256 pins, is what binds the downloaded seed to you.

## Never

- a password, API key, `.p8` content or Apple ID as a command-line argument, environment variable or log line;
- `--password` on any `notarytool` command;
- an exported `.p12`, or signing on another machine or in CI;
- notarization of a build that has not passed `release_build.py build --dry-run` and `check` on the same commit.
