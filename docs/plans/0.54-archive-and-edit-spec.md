# 0.54 F17a — archive/unarchive a chat and edit an own text message — implementation spec

**Status:** accepted 16.10.2026 under the owner's overnight delegation; **owner review pending**.
**Branch:** `qr-onboarding-052`
**Tasks:** [`0.54-archive-and-edit-spec.tasks.md`](0.54-archive-and-edit-spec.tasks.md)
**Requirement:** original plan F17 ("archive/unarchive, edit, delete and pin/unpin: independent
default-off capabilities; before/after and side-effect preview; exact approval, apply once and
verification of provider state; no mass moderation"). This slice covers archive/unarchive and own
**text** editing only. Captions, pin/unpin and deletion are later slices.

---

## 1. One sentence

With default-off capabilities `archive_chats` and `edit_own_text` (each also requiring `send`, the
existing "this tool changes Telegram state" authority), an MCP client can prepare (a) moving exactly
one chat between the Main and Archive lists, or (b) replacing the plain text of exactly one of the
owner's own outgoing text messages; the owner approves a before/after preview in the local dialog,
the broker applies it once and reports the provider state it then observes.

## 2. Input → output

| | what | format |
|---|---|---|
| input | `prepare_chat_archive`: `chat` (same selector forms as `prepare_text_send` recipients), `target_list` (`"archive"` \| `"main"`) | closed request |
| output | `ArchiveDraftPreview`: draft id, expiry, account id, chat id + sanitized title + chat kind, current list (`main`/`archive`; a chat in neither list is refused `unsupported_chat`), target list, preview_sha256 | closed model |
| input | `apply_prepared_archive`: `draft_id`, `approved` | closed request |
| output | `applied` (with observed list) / `already_in_target` / `failed` / `local_failed` / `not_approved` / `outcome_unknown` / `expired` / `chat_changed` / `error` | closed model |
| input | `prepare_text_edit`: `chat`, `message_id`, `new_text` (plain text, same bounds/normalisation as `prepare_text_send`; no styles) | closed request |
| output | `TextEditDraftPreview`: draft id, expiry, account id, chat id + title, message id, current text (reversible JSON escapes + marker), new text (same), current edit_date, `source_sha256` of the current message projection, preview_sha256 | closed model |
| input | `apply_prepared_text_edit`: `draft_id`, `approved` | closed request |
| output | `applied` (with observed edit_date) / `failed` / `local_failed` / `not_approved` / `outcome_unknown` / `expired` / `message_changed` / `error` | closed model |

Drafts live in the existing registry under internal kinds `archive` and `text_edit`, owner-scoped,
TTL-bound, single-use, superseding per (owner, chat[, message]); excluded from the generic draft
tools like forward/video drafts. Existing tool schemas stay byte-identical.

## 3. Scenario and rules

**Archive.** Prepare: capabilities → owner → resolve chat (secret chats refused) → read chat
positions; current list = the one carrying a position (`chatListMain`/`chatListArchive`), else
`none`; refuse `unsupported_chat` for a chat in neither list, `already_in_target` returned as a
content-free result without a draft. Apply (same order as other sends): approved → owner/policy →
kind → receipt replay → chat identity + title revalidated → current list still equals the preview's
(else `chat_changed`) → dialog → recheck → claim → one `addChatToList(chat_id, chatListArchive|Main)`
→ then poll `getChat` (bounded, ≤ 10 s) and report `applied` only if the chat now has a position in
the target list; otherwise `outcome_unknown`. Never retry.

**Edit own text.** Prepare: capabilities → owner → resolve chat → `getMessage` → must be outgoing
(`is_outgoing`), `messageText` content, not forwarded, no reply markup, no self-destruct/scheduling/
sending state, and `getMessageProperties.can_be_edited` true; entities in the current text must be
in F14's visible fieldless allowlist (else `hidden_source_content`); projection hashed like F14
(text, entities, edit_date, link preview options). `new_text` must differ from the current text.
Apply: same order; revalidate the projection hash (else `message_changed`) and `can_be_edited`;
dialog; claim; one `editMessageText(chat_id, message_id, reply_markup: null,
input_message_content: inputMessageText{text: formattedText{new_text, []}, link_preview_options:
null, clear_draft: false})`; success requires the returned `message` to have the same id, chat,
`messageText` content whose text equals `new_text` exactly, and a non-zero `edit_date` greater than
or equal to the previous one; otherwise `outcome_unknown`. Never retry.

**TDLib allowlist:** add `addChatToList` and `editMessageText` with exactly the closed shapes
above (validated in `_validate_bounded_request`); `getChat`/`getMessage`/`getMessageProperties`
reads already exist.

**Dialogs:** dedicated channels. Archive: "Move chat «title» (chat id, kind) from Main to Archive?"
(or back), account, draft, expiry, note that archived chats with notifications enabled may return to
Main on new messages (Telegram behaviour). Edit: chat, message id, "Current text" and "New text"
both rendered with `forward_drafts.readable()` inside « » with the READABLE_RULE legend, account,
draft, expiry, note that recipients see the message marked "edited".

**Capabilities:** `archive_chats` and `edit_own_text` — default-off, independent, each also
requires `send`; registered everywhere F14/F15 registered theirs.

## 8. Risks and degradation

Telegram may move an archived chat back to Main on new messages; the preview and dialog say so and
`applied` reflects the state observed right after the call only. Edit windows can close between
prepare and apply ⇒ `can_be_edited` false ⇒ refusal, no attempt.

**Ceiling:** three distinct failed hypotheses on one sub-step ⇒ stop and record.

### Amendments 16.10.2026 (critic review)

Lead decisions after the independent critic review of 627129b; each has a test in
`tests/test_archive_edit.py` that fails on 627129b (or kills the named surviving mutation).

1. **Edge whitespace in `new_text` is refused, never stripped.** Telegram trims leading and
   trailing whitespace, so the stored text would differ from the text the dialog calls exact.
   After normalisation, a `new_text` whose first or last character is any Unicode whitespace
   (`str.isspace`: space, LF, tab, U+2028/U+2029, U+1680, and NBSP/U+2000–U+200A/U+3000, which NFKC
   turns into a space; also U+00A8, which NFKC turns into a leading space) is refused at prepare
   with `invalid_input` and the fixed detail "new text must not start or end with whitespace;
   Telegram trims it", before any provider read. Interior spaces and line breaks are kept exactly
   (an interior tab, U+2028 or U+2029 is refused by 7). A whitespace-only text keeps the generic
   `invalid_input` detail (normalisation refuses it as empty). `TextEditSpec`,
   `TextEditDraftPreview` and the closed `editMessageText` shape refuse edge whitespace too.
   `prepare_text_edit`'s output schema gains this `detail` value (and the one in 7).
2. **Only a 4xx provider error is `failed`.** After `editMessageText` or `addChatToList` is sent,
   a TDLib error whose code is 400–499 is a provider rejection (`failed`, code in the detail);
   any other code (≥ 500, < 0, 0–399 or missing), a timeout or a transport failure is
   `outcome_unknown` ("do not retry automatically"), because the change may have been applied.
3. **Archive membership counts only own positions.** A `chatListMain`/`chatListArchive` position
   counts only when its `source` is null (TDLib JSON omits a null `source`); an MTProxy-sponsored
   or PSA position (any `chatSource*`) never counts, and a malformed `source` makes the positions
   unavailable. A chat whose only Main/Archive position is sponsored/PSA is `unsupported_chat` at
   prepare and `chat_changed` at apply; after the call, a sponsored position in the target list is
   not an observed move (`outcome_unknown`).
4. **Dialogs.** Archive: the dialog adds that the chat leaves its current list and loses any pin
   there (and is not pinned in the target list) and, when archiving, that chat folders excluding
   archived chats will hide it; the return-to-Main note stays. These notes are dialog-only; the
   preview's `note` field is unchanged. Edit: the header shows the chat kind (private, group,
   supergroup, or "channel; visible to all subscribers"), bound in the preview as `chat.kind`
   (`prepare_text_edit` output schema: `EditChat.kind` added, required); the dialog says
   link-preview settings return to Telegram's default; only formatting Telegram does not detect
   again is listed as "removed", while Url, EmailAddress, PhoneNumber, Mention, Hashtag, Cashtag,
   BotCommand and BankCardNumber are listed separately as "auto-detected again by Telegram".
5. **Tests for surviving mutations:** a claim made stale (expired) between claim and send for
   both edit and archive is `local_failed` with no raw send; `edit_own_text` turned off inside
   `edit_guard` is `local_failed` with no raw send; an edit result with the right message id but
   another chat id is `outcome_unknown`; the status-policy test now distinguishes a capability
   refusal (content-free default) from a pending or locally failed draft's normal status, and an
   applied change reads content-free `outcome_unknown`, never `sent`. Send tools refuse change
   drafts with the kind-mismatch detail even after the change was applied.
6. **Recorded, not changed.**
   - *Concurrent applies* of one draft make exactly one provider attempt, but both callers may see
     the dialog, and the caller that lost the claim reads `outcome_unknown` ("current receipt
     authority is unavailable; do not retry automatically") although it made no attempt
     (`local_failed` if the winning claim ended before any provider attempt). It errs towards
     "unknown", never towards a second attempt or a false `applied`. *Corrected after the
     whole-branch review:* F14 forwards and F15 videos returned `expired` to that caller; they now
     share the pattern. A send whose current owner (for a video, also the artifact lifecycle and
     account epoch) held the draft and then found it consumed — at the claim after a concurrent
     dialog, or on a repeated call while the claim is in flight — routes through `attempt_outcome`
     like `_change_attempted` and reads `outcome_unknown` (or `local_failed`), never `expired` or a
     second attempt. A draft never claimed (superseded, expired, restarted, foreign) still reads
     `expired`. One difference stays: archive/edit also give `outcome_unknown` to a later call made
     after a lost authority such as an account switch, while F14/F15 keep their content-free
     `expired` for a later call whose owner or lifecycle no longer holds the draft. Tests:
     `FinalReviewTests` in `tests/test_forward_send.py` and `tests/test_video_send.py`.
   - *Informational side effect.* With `edit_own_text` + `send`, `prepare_text_edit` reveals the
     exact current text, entities and edit date of an own outgoing text message, and the chat's
     title and kind, without any read capability. With `archive_chats` + `send`,
     `prepare_chat_archive` reveals a chat's sanitized title, kind and Main/Archive membership
     (including the `already_in_target` and `unsupported_chat` answers) without any read
     capability. Enabling either capability therefore also grants these narrow reads.
7. **Characters TDLib rewrites are refused, never sent (lead decision on the critic-fix
   residual).** The edit request carries no entities, so the pinned TDLib's `fix_formatted_text`
   cleans its text with `clean_input_string` (td/telegram/misc.cpp at d1085f9) before sending,
   anywhere in the text:

   | input | TDLib does | after the shared normalisation (NFKC, CR/CRLF → LF, controls but LF/tab refused) |
   |---|---|---|
   | U+0000–U+0009, U+000B, U+000C, U+000E–U+001F | replaced by a space | only tab (U+0009) survives → **refused by this rule** |
   | U+000D | removed | never present (normalised to LF) |
   | U+000A, U+0020 | kept | kept |
   | U+2028, U+2029 | removed | survive (Zl/Zp) → **refused by this rule** |
   | U+202A–U+202E | removed | already refused as format characters (generic `invalid_input` detail) |
   | U+030A, U+0333, U+033F (UTF-8 `CC 8A`, `CC B3`, `CC BF`) | removed | survive after NFKC → **refused by this rule** |
   | a run of two or more U+200E/U+200F | all but the last become U+200C (`replace_offending_characters`) | already refused as format characters |
   | text beyond 35 000 bytes | truncated | impossible (at most 4096 characters, ≤ 16 384 bytes) |

   So `prepare_text_edit` refuses, after NFKC, a `new_text` containing tab, U+2028–U+202E, U+030A,
   U+0333 or U+033F with `invalid_input` and the fixed detail "new text contains characters Telegram
   rewrites (tab, U+2028–U+202E, U+030A, U+0333, U+033F)", before any provider read (edge whitespace
   is checked first and keeps its own detail). Because the check follows NFKC, a + U+030A (composed
   to U+00E5) passes, while U+02DA and U+2017 (NFKC: a space plus U+030A or U+0333) are refused.
   `TextEditSpec`, `TextEditDraftPreview` and the closed `editMessageText` shape apply the same set,
   so the dialog's exact new text is what Telegram stores. `prepare_text_edit`'s output schema
   gains this `detail` value. **Known pre-existing behaviour, not changed:** `prepare_text_send`
   (and the other text sends) share the normalisation and admit interior tabs, U+2028/U+2029 and
   these combining marks, which TDLib then rewrites; their reviewed text can differ from the
   stored text. Left for a later decision.

### Amendments 16.10.2026 (docs alignment)

- A TDLib read failure or timeout during the apply-time re-read ends as `expired` (no attempt);
  only changed, secret or malformed data gives `chat_changed`/`message_changed`.
- Secret chats: the archive tool refuses `unsupported_chat`; `prepare_text_edit` returns `unavailable`.
- `get_send_status` for these drafts never reports `sent`: pending/local states as usual, otherwise
  `outcome_unknown` with evidence `none`.
