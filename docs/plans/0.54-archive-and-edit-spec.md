# 0.54 F17a — archive/unarchive a chat and edit an own text message — implementation spec

**Status:** accepted 16.10.2026 under the owner's overnight delegation; **owner review pending**.
**Branch:** `qr-onboarding-052`

**Requirement:** original plan F17 ("archive/unarchive, edit, delete and pin/unpin: independent

---

## 1. One sentence

With default-off capabilities `archive_chats` and `edit_own_text` (each also requiring `send`, the
existing "this tool changes Telegram state" authority), an MCP client can prepare (a) moving exactly
one chat between the Main and Archive lists, or (b) replacing the plain text of exactly one of the
owner's own outgoing text messages; the owner approves a before/after preview in the local dialog,
the broker applies it once and reports the provider state it then observes.

## 2. Input → output

| | what | format |
|---|---|---|
| input | `prepare_chat_archive`: `chat` (same selector forms as `prepare_text_send` recipients), `target_list` (`"archive"` \| `"main"`) | closed request |
| output | `ArchiveDraftPreview`: draft id, expiry, account id, chat id + sanitized title + chat kind, current list (`main`/`archive`/`none`), target list, preview_sha256 | closed model |
| input | `apply_prepared_archive`: `draft_id`, `approved` | closed request |
| output | `applied` (with observed list) / `already_in_target` / `failed` / `local_failed` / `not_approved` / `outcome_unknown` / `expired` / `chat_changed` / `error` | closed model |
| input | `prepare_text_edit`: `chat`, `message_id`, `new_text` (plain text, same bounds/normalisation as `prepare_text_send`; no styles) | closed request |
| output | `TextEditDraftPreview`: draft id, expiry, account id, chat id + title, message id, current text (reversible JSON escapes + marker), new text (same), current edit_date, `source_sha256` of the current message projection, preview_sha256 | closed model |
| input | `apply_prepared_text_edit`: `draft_id`, `approved` | closed request |
| output | `applied` (with observed edit_date) / `failed` / `local_failed` / `not_approved` / `outcome_unknown` / `expired` / `message_changed` / `error` | closed model |

Drafts live in the existing registry under internal kinds `archive` and `text_edit`, owner-scoped,
TTL-bound, single-use, superseding per (owner, chat[, message]); excluded from the generic draft
tools like forward/video drafts. Existing tool schemas stay byte-identical.

## 3. Scenario and rules

**Archive.** Prepare: capabilities → owner → resolve chat (secret chats refused) → read chat
positions; current list = the one carrying a position (`chatListMain`/`chatListArchive`), else
`none`; refuse `unsupported_chat` for a chat in neither list, `already_in_target` returned as a
content-free result without a draft. Apply (same order as other sends): approved → owner/policy →
kind → receipt replay → chat identity + title revalidated → current list still equals the preview's
(else `chat_changed`) → dialog → recheck → claim → one `addChatToList(chat_id, chatListArchive|Main)`
→ then poll `getChat` (bounded, ≤ 10 s) and report `applied` only if the chat now has a position in
the target list; otherwise `outcome_unknown`. Never retry.

**Edit own text.** Prepare: capabilities → owner → resolve chat → `getMessage` → must be outgoing
(`is_outgoing`), `messageText` content, not forwarded, no reply markup, no self-destruct/scheduling/
sending state, and `getMessageProperties.can_be_edited` true; entities in the current text must be
in F14's visible fieldless allowlist (else `hidden_source_content`); projection hashed like F14
(text, entities, edit_date, link preview options). `new_text` must differ from the current text.
Apply: same order; revalidate the projection hash (else `message_changed`) and `can_be_edited`;
dialog; claim; one `editMessageText(chat_id, message_id, reply_markup: null,
input_message_content: inputMessageText{text: formattedText{new_text, []}, link_preview_options:
null, clear_draft: false})`; success requires the returned `message` to have the same id, chat,
`messageText` content whose text equals `new_text` exactly, and a non-zero `edit_date` greater than
or equal to the previous one; otherwise `outcome_unknown`. Never retry.

**TDLib allowlist:** add `addChatToList` and `editMessageText` with exactly the closed shapes
above (validated in `_validate_bounded_request`); `getChat`/`getMessage`/`getMessageProperties`
reads already exist.

**Dialogs:** dedicated channels. Archive: "Move chat «title» (chat id, kind) from Main to Archive?"
(or back), account, draft, expiry, note that archived chats with notifications enabled may return to
Main on new messages (Telegram behaviour). Edit: chat, message id, "Current text" and "New text"
both rendered with `forward_drafts.readable()` inside « » with the READABLE_RULE legend, account,
draft, expiry, note that recipients see the message marked "edited".

**Capabilities:** `archive_chats` and `edit_own_text` — default-off, independent, each also
requires `send`; registered everywhere F14/F15 registered theirs.

## 5. Out of scope

Caption edits, styled text edits, pin/unpin, deletion, editing other people's messages, folders
(chatListFolder), bulk operations, scheduled messages.

## 6. Verification material

`td_api.h` for field sets.

## 7. Who decides

Deterministic; the owner decides in the dialog. Sequential implementation (shared broker/tdjson).

## 8. Risks and degradation

Telegram may move an archived chat back to Main on new messages; the preview and dialog say so and
`applied` reflects the state observed right after the call only. Edit windows can close between
prepare and apply ⇒ `can_be_edited` false ⇒ refusal, no attempt.

**Ceiling:** three distinct failed hypotheses on one sub-step ⇒ stop and record.
