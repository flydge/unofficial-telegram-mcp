## How to read this table

- **Evidence classes.** *Technical*: unit, synthetic, transport, socket and golden tests, in-process official SDK
  clients and the release gate. *Consumer*: an installed official SDK or a real MCP client over STDIO (the consumer
  matrix installs the wheel built from `git archive`; its agent columns and the conversation runs use the real
  `codex exec` and `claude -p` against the installed server on synthetic data). *Real*: a real Telegram account,
  with the owner's approval where something changes.
  Synthetic evidence is technical evidence only; an unknown outcome stays unknown.
- **met:** the requirement's acceptance is covered by technical and consumer evidence, and by real evidence where
  the requirement or `CLAUDE.md` asks for it; nothing owner-only is pending for it.
- **met with owner remainder:** technically complete, and everything an agent can produce exists; the evidence still
  missing can only come from the owner session. The row closes only when those rows pass.
- **partly met:** a part of the requirement lacks evidence that an agent can still produce, or a part is not yet
  done. Such a row names its **agent-side gap**.
- **not applicable / not met:** no row has either status. F19's HTTP part is not applicable inside a partly met row.
- **Consumer evidence per part.** A part of a requirement counts as consumer-covered only when an installed
  consumer calls it and gets a positive answer; a refusal or an `unsupported` answer covers the refusal only.
- **Which code the evidence is for.** A record is evidence for its own commit. Real runs happened on 0.51.0 (the
  owner-accepted public release; its per-capability acceptance records are outside the public tree and the
  [0.51.0 notes](../release-notes-0.51.0.md#accepted-scenarios) name them only in summary) and on 0.52 source
  installs (20.10.2026), several of them before later commits changed their paths (named in each row). Later
  candidates carry technical evidence and the consumer-matrix receipt of their own commit; the mounted-DMG run
  (P2) is for 0c9f040, and the commits after it change the installer (1b604f9), the text-send refusal (12f53f6), the
  selection projection (2c87e08) and the matrix, so the build commit gets its own run (decision sheet, step 14). A
  row records whether the capability was accepted with its applicable evidence; re-running the matrix and the real
  scenarios on the final candidate is part of the final G1 (P3, F19), not of each row.
- **F18 receipt and final-audit cells.** The extended consumer matrix (receipt `tgmcp-consumer-matrix/v4`, merged
  into this branch in 3da4745) ran once at fc3f3c8 on the `v0.58.0rc1` gate wheelhouse: 48 of 48 synthetic cells,
  MCP Inspector 4 of 4, real Codex 9 of 9 and real Claude Code 9 of 9 (census, read, search with cursor, refusal,
  approval timeout, alias server, album prepare, own-message edit prepare, reply to a reply-family source; Claude

  fc3f3c8…` verified it ([task record](final-acceptance-spec.tasks.md), criterion 2). Rows cite its cells by id as
  *F18 receipt*. The code round of 26.10.2026 added seven synthetic cells for the agent-side gaps of F6, F9 and F13
  and for the typed text-send refusal (55 in all;
  [matrix spec](final-consumer-matrix-spec.md#5a-the-final-audit-cells)); the synthetic and Inspector columns
  passed at 2755559 (55/55, 4/4) and `check --commit 2755559…` verified that receipt, a scratch receipt that was

## Shared limits

Checked against the code at this branch; each is held by the tests named.

- **Untrusted content, no execution:** readers render Telegram text as data; formulas are data, no macros or
  external resources (`tests/test_xlsx_reader.py`, `tests/test_pptx_reader.py`, `tests/test_docx_safety.py`).
- **Sessions preserved, one broker per session:** `tests/test_session_owner.py`, `tests/test_onboarding.py`; per
  alias since 0.55 (`tests/test_account_install.py`).
- **Capabilities from trusted policy, never tool arguments:** `tests/test_capability_profiles.py`,
  `tests/test_guard_refusals.py`; the default stays `read` + `artifacts` (owner, 20.10.2026). A preparation that
  reveals content also needs `read`, except `forward_send`, the reply sends and the 0.58 reply families, which the
  owner confirms ([decision sheet](owner-decision-sheet.md#2-decisions-recorded-since-055-for-the-owner-to-confirm)).
- **No read receipts; writes need approval:** no read-receipt request is allowlisted; every send and apply goes
  through the owner dialog (`tests/test_approval_prompt.py`, `tests/test_approval_serialization.py`).
- **Bounded pages, opaque bound cursors:** matrix cells `cursor.list_chats`, `recovery.restart_listing`,
  `caps.input_bounds`; `tests/test_account_isolation.py` for cursors across accounts.
- **Immutable hash-bound payloads; no automatic retry of an unknown send:** draft digests and one-attempt
  transports (`tests/test_outgoing_drafts.py`, `tests/test_album_send.py`, `tests/test_message_delete.py`).
- **Never reachable:** secret chats (`use_secret_chats=False`); a raw TDLib bridge, clear-history, delete-chat and
  bulk deletes or unpins, because none of those requests is in the closed request allowlist (the exact-set tests in
  `tests/test_caption_edit.py` pin the allowlist and an unreachable set disjoint from it). Separately, the generic
  `_call` refuses the allowlisted change requests (the Main/Archive move, text and caption edits, pin and unpin, the
  one-message delete) and the forward and album requests, which travel only through their one-attempt transports; it
  does not refuse a shape-valid `sendMessage`, and sends use their dedicated transport. Unrestricted transcript
  export and a persistent private index: bounded pages and selected scopes only
  ([security](../security.md#memory-persistence-and-logging)).
- **Platform:** macOS ARM64 with the pinned TDLib only; the TDLib procedure keeps that pin until a trigger.
