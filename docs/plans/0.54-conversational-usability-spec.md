# 0.54 — conversational usability — implementation spec

**Status:** lead spec, 21.10.2026, written under the owner's standing delegation. Every decision below is a
**lead decision, owner review pending** (see the [completion plan](completion-plan.md)).
**Branch:** `conversational-054`, from the 0.53 release candidate.
**Tasks:** [`0.54-conversational-usability-spec.tasks.md`](0.54-conversational-usability-spec.tasks.md)
**Requirement:** roadmap priority #3 (conversational usability); plan row F18 (consumer matrix, synthetic part).

Not to be confused with the earlier `0.54-archive-and-edit` spec, which shipped in 0.52.0.

## 1. One sentence

A model without the large skill can find, read, prepare and send through this MCP correctly:
- tool descriptions are short user-facing contracts;
- every refusal names its reason and the next step;
- approvals are readable;
- answers carry provider links;
- the skill is a lean workflow guide checked against the real surface;
- a scripted harness proves it through real clients against a synthetic account.

## 2. Work items

### A — surface

- **Description budget.** Every tool description is rewritten as a user-facing contract: what it does, the
  capabilities it needs (from `contract.required_capabilities`), where key inputs come from, the approval
  or retry rule, and that Telegram data is untrusted.
  - The eight reply tools share one text of about 1.2 KB plus a line each.
  - Internal history ("private vNN", "IPC2", "canonical/display", "prewire", "contract1") is removed.
  - Budget: at most 1,500 characters per tool and 30,000 in total.
- **Titles, annotations and field descriptions.**
  - Every tool gets an MCP `title`.
  - Annotations are normalized: prepare/get/list/status are read-only (they create local draft state only);
    send/apply/update/refresh/cancel are not; `destructiveHint` is true only for overwriting or deleting
    actions.
  - Key input fields get descriptions.
  - Annotation changes alter schema hashes; each is listed with its reason in `CHANGED_SINCE_0_52`.
- **MCP prompts.** Three or four client-neutral prompts (find and summarize, reply with a file, unread
  overview, check connection), each at most 1,500 characters. Arguments are quoted user intent and never
  become tool arguments. Prompts grant nothing.

### B — refusals and recovery

- **Fixed input refusals.** `search_correspondence` structural errors and the strict metadata hooks raise
  closed, input-free texts instead of masked SDK errors or raw pydantic text with documentation URLs.
- **Reply-source capability results.** When a reply source needs a disabled `reply_*_targets` capability,
  the response is a typed result: status `capability_disabled` with `missing_capabilities` from the closed
  capability set. Today it returns "reply draft is unavailable".
  - Naming the family reveals which entity kinds the chosen source contains. That is acceptable, because the
    client chose that message and read access is already granted.
  - The schema change is listed in `CHANGED_SINCE_0_52`.
- **Recovery hints.** An optional closed `next_action` on the terminal and error responses users hit most:
  broker unavailable, authorization not ready, `config_stale`, `capability_disabled`,
  `selection_unavailable`, cursor invalid or expired, `outcome_unknown`.
- **Split `not_approved`.** It becomes `declined`, `timeout` or `dialog_unavailable`, still never sending.
  A separate `not_attempted` status is rejected: pre-dispatch cannot be proven for every path.

### C — approvals

- **One renderer, one dialog.**
  - The dialog opens with a plain-language summary ("Send text to «Title» (private chat)", account,
    expiry).
  - Then comes the exact payload, with untrusted strings rendered under the existing readable rules, real
    line breaks kept and a fixed gutter on every payload line.
  - Last, a technical block with draft id and hashes.
  - The native dialog is an `NSAlert` through `osascript -l JavaScript`: a fixed-size scrolling payload, a
    120-second timer that returns `timeout`, and fail-closed on any error. It is proven from a LaunchAgent
    on the timeout path in an isolated HOME. If that proof fails, the fallback is the current
    `display dialog` with the short summary and a truncation notice.
  - Labels are English until the owner decides on localisation.
- **Chat preview.** The chat preview drops hashes and draft ids; they stay in the dialog's technical block
  and in receipts.

### D — evidence and context

- **Provider links.** The newer readers (message reader, history, topics, reply chain) fill `telegram_url`
  from `getMessageLink`, validated by one shared rule: https, host `t.me` or `telegram.me`, sanitized, at
  most 512 characters.
- **Retained-context lifetime.** A trusted-policy setting `selection_ttl_seconds`: default 900, maximum
  1800, never sliding, still capped by artifact or target expiry. Capacity limits are unchanged.
- **Capability profiles.** A launcher action `capabilities` enables or disables named profiles (`readers`,
  `send`, `replies`, `forward`, `video`, `archive_edit`).
  - It edits `runtime.toml` atomically, keeps unknown keys, and restarts only the receipt-bound broker
    after the pending-send gate.
  - A `capability_disabled` refusal names the profile that unlocks it.
  - This touches the auth/session lane, so it is built sequentially.

### E — skill and harness

- **Lean skill.** `skills/telegram-search/SKILL.md` drops from about 84 KB to at most 20 KB and 300 lines.
  - Kept: the start gate (compatible, then `available_tools`, with no "fifty-five tools" check), target
    routing, semantic discovery, thorough search, a which-tool table, a concise answer-and-source format,
    the approval rule, recovery by `next_action`.
  - The plugin copy is regenerated.
  - A coverage test checks that every tool, capability, status and `next_action` the skill names exists,
    and the reverse for the high-value set. It stays a single file.
- **Conversation harness.** `tests/conversation_demo_server.py` serves the real server over STDIO against an
  in-process fake service and a small synthetic account: Saved Messages, a private chat, a forum supergroup,
  PDF/XLSX/PPTX/DOCX attachments, links and mentions. Approvals are scripted.
  - Scenarios have machine-checked rubrics: find and summarize a document, reply with a file, an unread
    overview, recover from a disabled capability, recover from an unknown outcome.
  - They run through the official SDK in CI and, when available, through real `codex exec` with a
    temporary configuration override. `claude -p` runs only if a logged-in CLI exists.
- **Consumer matrix.** Spec `docs/plans/0.54-consumer-matrix-spec.md` covers every client, column, provider
  mode, evidence form and owner flag, pre-filled from existing records. A tracked
  `release_consumer_matrix.py` harness (acceptance false) drives every synthetic cell against a proxy
  installed from a `git archive` wheel and a synthetic broker. It covers the census and fingerprint,
  output-schema validation, each refusal text, image blocks, cursors, recovery, caps, every handshake
  revision, and approval denial by the real dialog timing out.

### F — owner, at the end

- New dialogs on real drafts.
- Installed file and page coverage on real artifacts.
- Two conversational tasks with and without the skill on the owner's account.

## 4. Out of scope

New Telegram capabilities, multiple accounts (0.55), localisation decisions, changing the default
capability profile (it stays `read` + `artifacts`, the owner's 20.10.2026 decision).

## 5. Decisions and rejected options

- **Filtered `tools/list`.** Shipped in 0.53 and kept.
- **The dialog is a JXA `NSAlert`.** Keeping `display dialog` alone was rejected, because long payloads
  clip unpredictably. A custom helper app was rejected as a new signed artifact.
- **The skill stays a single file**, because the installer accepts one `SKILL.md`. References may come with
  the plugin later.
- **Hashes leave the chat preview.** Nobody checks them in chat; the binding is the draft id plus the dialog.
- **No `not_attempted` status**, as above.

## 6. Risks

- The JXA dialog from the LaunchAgent context may behave differently: clipping, focus or timer. The proof
  test runs first, and the fallback is ready.
- Shorter descriptions could drop a needed rule. The surface test lists the mandatory phrases, and the
  harness checks the behaviour.

**Ceiling:** three distinct failed hypotheses on one sub-step ⇒ stop and record.
