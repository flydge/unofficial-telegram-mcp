## 1. One sentence

For every MCP client the project supports, the matrix names what is checked (the rows), against which
provider (a synthetic broker or the real account), by whom (the harness, an agent or the owner) and in
what evidence form; `packaging/release_consumer_matrix.py` runs every synthetic row through the official
SDK against a proxy installed from a `git archive` wheel and writes a receipt bound to the commit, the
wheel hash and the schema fingerprint. The harness never marks an owner or real-account cell passed.

## 3. Provider modes

- **Synthetic broker.** The installed `telegram_search_mcp.broker.Broker` class with its real policy,
  draft, selection and artifact code, over `SyntheticTDLib`: a fake raw tdjson transport that serves one
  fixed synthetic account (account 9001, 25 private chats in Main, the public username
  `matrix_synthetic`, one source message with a hashtag) and never opens a network, the Keychain or a
  TDLib session. `sendMessage` raises after it is logged: the client reads a transport lost after
  dispatch, so the send outcome is unknown. The owner is scripted: the bound approval document is
  rendered, then declined (only the outcome probe is approved). With `--real-dialog` the denial probe
  opens the real JXA dialog with a 5-second timer and must end as `timeout`.
- **Real account.** The owner's account on the owner's Mac. Only the owner runs these cells; their
  evidence is an owner record (date, commit, client version, what was seen), never a harness receipt.

## 5. Evidence forms

- **Harness receipt** (`tgmcp-consumer-matrix/v2`, JSON, canonical). Keys: `schema`, `acceptance`
  (always `false`), `harness` (path, sha256), `gate` (path and sha256 of `packaging/release_gate.py`),
  `commit`, `tree`, `version`, `wheel` (file, sha256, bytes),
  `build` (python, `build`, `setuptools`, source date epoch), `install` (constraints file and sha256,
  wheelhouse downloaded or provided, distributions, `freeze`, `pip_check`, verified `record_entries`),
  `sdk` (distribution, version, revisions), `schema_fingerprint`, `census` (tool count, `tools_sha256`,
  capability count), `surface` (sha256 of the consumer-observed listing, validated structured results,
  tools with validated results, tools without an output schema), `approval` (mode and outcome),
  `cells` (id, status, checks), `owner_cells` (always `pending`) and `summary`. No paths, no Telegram
  data, no timestamps. v2 added `gate`, the frozen counts and the re-derived install and listing (22.10,
  after the harness review); a v1 receipt is refused.
- **Agent record** (Inspector, Codex, Claude Code synthetic cells): the commit, the client version, the
  exact command with its configuration override, and the observed results, in the tasks file.
- **Owner record**: date, commit, client and version, what was seen; real sends name their readback.
  Unknown send outcomes stay unknown.

## 7. Harness contract

```bash
.venv/bin/python packaging/release_consumer_matrix.py run --commit <sha> --receipt <absolute path> \
    [--wheelhouse <dir>] [--workdir <dir>] [--real-dialog]
.venv/bin/python packaging/release_consumer_matrix.py check --receipt <path> [--commit <sha>] [--wheelhouse <dir>]
```

- `run` builds the sdist and the wheel from `git archive <sha>` as the release gate does (the wheel from
  the sdist, `SOURCE_DATE_EPOCH` = commit time) with the running interpreter's `build` and `setuptools`,
  checks the wheel members, installs it in a fresh venv with the closure of
  `packaging/constraints-<version>.txt` at the commit (hash-checked, `pip check`, every `RECORD` hash;
  downloaded into the workdir unless `--wheelhouse` names an existing one), takes the release gate's
  source census of the extracted tree, runs the five sessions and writes the receipt only when every
  synthetic cell passed. It refuses first when the working tree's harness (`harness_mismatch`) or
  `packaging/release_gate.py` (`gate_mismatch`, hashed from the bytes it executes) is not the commit's.
- `check` re-derives the bindings with the receipt commit's own harness and gate (a differing working-tree
  copy refuses, so an older receipt is checked from a checkout of its commit): it rebuilds the wheel from
  `git archive <receipt commit>`, takes the census of that tree with the running interpreter, reinstalls
  the pinned closure and lists the tools through the reinstalled proxy (the cell-less `listing` session,
  full policy, no broker). It refuses a different wheel hash or size, fingerprint, tool set or version;
  build tools other than the ones that rebuilt the same wheel, or an interpreter outside the constraints'
  target minor version; a freeze other than the commit's pins, another SDK version, install facts or a
  listing other than the reinstall's; a failed cell, a claimed acceptance, a passed or edited owner cell;
  and any per-cell check count or surface count other than the ones frozen in the harness (`CELL_CHECKS`,
  plus the timer check under `--real-dialog`, and `SURFACE_COUNTS`). Every receipt field has a test that
  edits it and expects the fixed refusal.
- Refusals print one fixed code. The harness never touches the live runtime tree, the Keychain, launchd
  state or client configurations; nothing reaches Telegram. The offline session's proxy makes its own
  `launchctl kickstart` attempt for the LaunchAgent label it derives from the temporary HOME
  (`com.tgcm3.…`), which does not exist, so nothing starts.
- Expected texts are the documented contract (`docs/reference.md`), hard-coded in the harness; a unit
  test fails when the source constants drift from them.

## 8. Decisions and rejected options

- **Dependencies come from the commit's pinned closure.** Bridging the developer venv into the
  temporary venv was rejected: it would test other versions than the release installs.
- **Build tools are the running interpreter's** (`build` 1.3.0 and `setuptools` 80.9.0, the release
  gate's pins), recorded in the receipt; `check` proves the wheel reproduces. Downloading a separate
  toolhouse per run was rejected as duplicate release-gate work.
- **One HOME per session, sessions in parallel.** One HOME with policy rewrites between cells was
  rejected: a rewrite makes every loaded proxy and broker `config_stale`, and the cells would depend on
  their order. Running the sessions at once overlaps the offline session's two broker waits (the proxy
  retries a missing broker for about 10 seconds per call) with the other sessions.
- **`outcome_unknown` comes from a transport lost after dispatch.** Waiting out the 30-second
  confirmation timeout was rejected as slow; an error answer to `sendMessage` would be a definite failure,
  not an unknown outcome.
- **Each initialize revision goes through the SDK's own `ClientSession` with an explicit
  `InitializeRequest`.** `mcp.Client` only offers the latest revision; patching the SDK's constant was
  rejected.
- **Expected texts are hard-coded, not read from the installed package**, which would make the refusal
  cells tautological.
- **The real dialog is opt-in.** It shows a window on the owner's screen for five seconds; the scripted
  denial is the default and the recorded run.
- **Inspector, Codex and Claude Code synthetic cells are not in this harness.** They need their own CLIs
  and logins; the final acceptance runs them as agent cells and records them in the agent form.
- **Per-cell check counts and surface counts are frozen in the harness** (22.10, after the harness
  review). The harness file is bound by its hash, so the counts are the commit's contract and a cell
  weakened in the driver must also change its count; the source-session test fails when the driver and
  the frozen counts drift apart. Re-running every session in `check` was rejected: the real dialog cannot
  be repeated unattended, and it would duplicate `run`.
- **`check` reinstalls the closure and lists the tools again** instead of trusting the recorded install
  facts and listing. That costs a download unless `--wheelhouse` names one, which the release gate already
  accepts for its own install.
- **The release gate is bound like the harness.** Delegating an older receipt to the gate stored at its
  commit, as `release_gate.py verify` does for its own evidence, was rejected: a receipt is evidence for
  its own commit only, and the final receipt is taken and checked at the release commit.
