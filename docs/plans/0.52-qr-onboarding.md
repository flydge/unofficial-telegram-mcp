# 0.52 requirement: QR-first Telegram onboarding

Status: **approved requirement, not implemented or accepted**. Recorded 2026-10-14.
Target: **0.52.0**. Priority: **#1, the next implementation slice after explicit resume**.

This decision updates the existing P2/B1 onboarding scope and its F18 acceptance
gate. It takes precedence over earlier plans that require each end user to create
a Telegram API application or use Terminal as the only login interface. The
[roadmap](../roadmap.md) owns the remaining backlog; the
[original plan](initial-roadmap.md) and past evidence remain historical records.

The current authorization covers documenting this decision and pushing the
documentation to GitHub only. Development remains paused after B2C. It does not
authorize implementation, installation, real login, runtime activation, a new
release/tag, or dispatch of another development stage. No implementation budget
or completion date is established by this record.

## Required user outcome

A new user on the supported Apple Silicon macOS 26+ platform asks local Codex to
install the MCP and its skills from the published project instructions. The
installation leads directly to a local Telegram connection screen. The user
scans its QR code with their already logged-in Telegram phone app, confirms the
connection and, only if Telegram requires it, enters their 2FA password locally.
Codex then verifies the connected MCP and completes one user-selected, bounded
read/search. A subsequent normal launch reuses the authorized local session.

The user must not need to create an API application, obtain or enter `api_id` or
`api_hash`, copy skills, edit MCP configuration, or manually prepare a TDLib
session. Human confirmation on the phone and any required 2FA remain intentional.
The QR and password belong in a local authorization interface, not in the model's
chat, MCP results, captured command output, logs or remote telemetry.

## Requirements

| ID | Mandatory behavior for 0.52 |
| --- | --- |
| QR-01 | The distributed application supplies its own developer-managed API identity automatically. Each user authorizes their own account and receives a separate local session. End-user API application creation or manual API-pair entry is not the normal installation path. |
| QR-02 | Installation and paired-skill registration lead to a local connection screen with a working Telegram login QR. A manual Terminal-only login procedure does not satisfy the target experience. |
| QR-03 | Request QR authentication through the pinned TDLib API; handle `authorizationStateWaitOtherDeviceConfirmation` and its changing link. Refresh expired/replaced QR codes, clear them on completion/cancel, and present understandable waiting, error and retry states. |
| QR-04 | Preserve Telegram's optional password/2FA step. Cancellation, disconnect, interruption and uncertain outcomes must remain explicit and recoverable; do not silently approve, replay an uncertain submission, reset an account or discard an existing session. |
| QR-05 | Reuse the managed encrypted session, Keychain, exclusive TDLib ownership and confirmed close/destroy-to-broker handoff. Ready requires the intended installed broker, a compatible contract and fresh provider authorization, followed by a bounded read/search from Codex. |
| QR-06 | Repeat installation/launch preserves the authorized session and unrelated settings. Expired or revoked authorization leads to a clear reconnect flow. Read/artifacts remain the default; login does not enable sending or authorize unrelated Telegram actions. |

The existing phone/code path may remain a fallback or developer path. It cannot
replace QR acceptance, become a mandatory preliminary step to QR, or be used to
declare this requirement complete. No additional account, cloud service or
platform scope is introduced.

## Conflict resolution and reuse

| Existing assumption or work | Required treatment |
| --- | --- |
| Every user obtains an API pair from `my.telegram.org/apps` | Superseded for the normal 0.52 flow by QR-01. Existing records must not be overwritten silently; define an explicit compatibility path when integrating application credentials. |
| Authorization is allowed only through foreground Apple Terminal | Extend the trusted local authorization boundary to the connection screen. Preserve isolation from model-visible/captured channels; do not remove secret protections merely to display a QR. Current Terminal-only code remains unchanged until implementation. |
| QR is an unsupported authorization state | Implement the pinned QR request, state payload/link handling and local display. The current unsupported-state behavior is a known gap, not a reason to defer QR behind unrelated features. |
| Installation ending at `activation_required` or synthetic Ready closes onboarding | It proves only the technical installation slice. The real install-to-QR-to-Codex scenario below is mandatory. |
| Accepted B1A/B1B installer, encrypted session and broker work | Reuse compatible components. Resolve any incompatibility in this onboarding slice before moving to unrelated feature work. Past tests remain scoped evidence, not QR acceptance. |
| Prepared B2/F13/F14/F15/F16/F17 continuation work | Retain it as backlog. QR-first onboarding and its direct prerequisites take precedence; prepared briefs must not trigger those slices first. |

## Next development slice after resume

One end-to-end owner integrates the smallest complete QR onboarding path, with
one implementation slice in progress and one independent review at a time:

1. Settle the product's API application and distribution configuration, preserving
   existing sessions/credentials and identifying any missing owner input.
2. Add the local connection screen and pinned QR/optional-2FA flow to the current
   installer and managed-session handoff. Keep API-pair provisioning automatic for
   the consumer. Interface technology is an implementation choice within these
   constraints; QR login tokens must remain local and short-lived.
3. Run focused technical checks and the real clean-install acceptance below.
4. Record acceptance and remaining release work before returning to lower-priority
   backlog. If blocked, name the exact missing input or evidence; do not silently
   substitute phone-only onboarding or start an unrelated feature.

This is a refinement of the existing onboarding scope, not authorization to
restart development now or to replace the entire application architecture.

## Owner inputs and release dependencies

- The product owner selects/registers the application's Telegram API identity and
  supplies it to the local build configuration without sending credentials in chat.
  Distributed client parameters cannot be assumed unextractable; settle their
  packaging and responsibility before release. They identify the application;
  users' authenticated sessions remain separate.
- Real validation needs an authorized test account with an already logged-in phone
  and human confirmation/2FA. Existing permissions must be checked for the exact
  installation/activation target; this documentation change grants no such action.
- Public installation artifacts, publisher trust, source/notices and existing
  privacy/package checks remain release dependencies. Current Telegram API/content
  terms, including their AI-use restrictions and consent provisions, require a
  separate applicability check for the public MCP. QR success is not that check.

## Acceptance and release gate

**0.52.0 must not be declared complete or released without this QR requirement
passing.** It is a necessary gate, not a claim that other release gates disappear.

Use the actual candidate package and installed launcher in a clean OS user/Mac
without developer Python/Homebrew/Git/compiler or pre-provisioned Telegram API
credentials/session. Retain bounded evidence tied to exact source/package IDs:

- Installation registers the intended MCP and both skills while preserving
  unrelated configuration. The user reaches the local QR screen without creating
  an API app, entering an API pair or manually constructing a session.
- A real phone scan and confirmation authorize the intended account. Cover a
  password-enabled account, QR refresh/expiry, cancellation and interruption/resume.
  Technical tests may cover refusal branches; real login evidence is still needed.
- Confirm temporary-client teardown, exclusive session handoff, matching live
  broker and fresh Ready; reconnect Codex and complete the bounded selected
  read/search with discoverable setup/search guidance. No send is required.
- Demonstrate ordinary restart/repeat installation without another login, plus
  controlled authorization loss/reconnect on the approved test session. Preserve
  existing-owner sessions and do not broaden this into multi-account support.
- Verify QR links, passwords and session keys do not enter chat/tool/log output.
  Record the human user's successful completion and any manual workaround. A
  developer-only workaround, fake provider or SDK manifest alone fails this gate.

The owner-approved design direction needs no duplicate written-plan approval.
New material product decisions, risks or external effects outside the applicable
authorization must still be surfaced. No release readiness is claimed here.
