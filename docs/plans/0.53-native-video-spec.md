# 0.53 F15a — send one native Telegram video — implementation spec

**Status:** accepted 16.10.2026 under the owner's overnight delegation; **owner review pending**.
Decisions were made by the lead without an interview; amend in a separate commit.
**Branch:** `qr-onboarding-052`
**Tasks:** [`0.53-native-video-spec.tasks.md`](0.53-native-video-spec.tasks.md)
**Requirement:** original plan F15 ("native Telegram video, then albums: immutable media with
validated metadata… Sending a document does not count as native video"). Albums are F15b, later.

---

## 1. One sentence

With default-off capability `video_send` (plus `send`), an MCP client can prepare one owned MP4/MOV
artifact (≤ 64 MiB) as a native Telegram video for one chat, with metadata (duration, width, height,
codec, streaming layout) validated locally from the file's own boxes, and the owner approves the
exact preview before one `sendMessage(inputMessageVideo)` attempt.

## 2. Input → output

| | what | format |
|---|---|---|
| input | `prepare_video_send`: `artifact_id` (owned grant, as `prepare_artifact_send`), `recipient` (same selector forms), `caption` (optional plain text, same bounds/normalisation as artifact captions; no styles) | new closed request model |
| output | `VideoDraftPreview`: draft id, expiry, recipient id + sanitized title, file display name, bytes, sha256, duration_seconds, width, height, video codec (`h264`/`hevc`), has_audio, supports_streaming, caption, preview_sha256 | new closed model |
| input | `send_prepared_video`: `draft_id`, `approved` | new closed request model |
| output | existing send-result vocabulary (`sent`/`failed`/`local_failed`/`not_approved`/`outcome_unknown`/`expired`/`recipient_changed`/`error`) | new closed response model |

Existing tool schemas stay byte-identical (`prepare_artifact_send`, `begin_local_upload` etc. are
pinned). Video drafts use an internal registry kind and are excluded from the generic draft tools,
like forward drafts; preparing again for the same (artifact, recipient) supersedes.

**Metadata probe** (`video_probe.py`, new, stdlib only, no ffprobe): bounded ISO-BMFF walk with
seeks (box count ≤ 4096, depth ≤ 8, `moov` ≤ 16 MiB read into memory, 64-bit sizes handled,
truncated/overlapping boxes refuse). Requirements: `ftyp` first with a major or compatible brand in
{isom, iso2, iso4, iso5, iso6, mp41, mp42, avc1, M4V , qt  }; exactly one `moov`; no `mvex`
(fragmented files refuse); exactly one track with handler `vide` whose first `stsd` entry is
`avc1`/`avc3` (h264) or `hvc1`/`hev1` (hevc); at most one `soun` track (`mp4a` or `Opus`); other
track types refuse. Duration from `mvhd` (timescale > 0, 1 s ≤ duration ≤ 3 h, rounded up);
width/height from the video `tkhd` (16.16), swapped for a 90°/270° rotation matrix, each 16–8192 and
aspect ≤ 20:1; `supports_streaming` = `moov` precedes the first `mdat`. Any other shape →
`unsupported_video`. The probe returns facts only; it never decodes media.

## 3. Scenario

```
local upload (kind=document, ≤ 64 MiB) or get_attachment  → artifact_id (create_local_artifact stays within 512 KiB)
prepare_video_send(artifact_id, recipient, caption?) → VideoDraftPreview
send_prepared_video(draft_id, approved=true) → local dialog → {"status": "sent" | "outcome_unknown", ...}
get_send_status(draft_id)
```

Prepare: `send` + `video_send` → owner → artifact grant lookup (as artifact sends) → size ≤ 64 MiB
→ probe → resolve recipient (secret chats refused) → draft (artifact sha256 bound) → preview.
Send: same order as `_send_prepared_artifact_impl` (approved → owner/policy → kind → receipt
replay → title map → recipient re-resolve → artifact re-hash equals the draft → dialog → recheck →
claim → stage (existing `outgoing_stage`) → transport → finish). NotAttempted ⇒ `local_failed`,
provider error ⇒ `failed`, anything else ⇒ `outcome_unknown`; never retry.

TDLib: `sendMessage` closed shape gains `inputMessageVideo` = `{video: inputVideo{video:
inputFileLocal(staged path), thumbnail: null, cover: null, start_timestamp: 0,
added_sticker_file_ids: [], duration, width, height, supports_streaming}, caption, show_caption_above_media:
false, self_destruct_type: null, has_spoiler: false}` with the probed values and the existing
`protect_content: false` options. Observation expects final `messageVideo`; additionally check
duration/width/height and file size equal the draft when the final message carries them. The
confirmation wait for video is up to 120 s (uploads take longer than text); afterwards the
normal `get_send_status` reconciliation applies.

Dialog: a dedicated `video` preview channel: recipient title and id, file name (untrusted, escaped),
bytes, sha256, duration, width×height, codec, audio yes/no, streaming yes/no, caption (escaped,
marked untrusted), account, draft id, expiry.

Capability plumbing exactly as F14 (`KNOWN_CAPABILITIES`, `OPERATION_CAPABILITIES`,
`broker_protocol.OPERATIONS`, `server._TOOL_NAMES`, the "also requires send" sets, manifest lists,
`.codex/config.toml.example`), plus the artifact-bound registries (`owned_operations`,
`admission_models`, `_artifact_unavailable`) and kind guards so `send_prepared_artifact` refuses a
video draft.

## 5. Out of scope

Albums (F15b), video replies, topic destinations, captions with styles, thumbnails/covers,
spoiler/self-destruct, videos > 64 MiB (needs a new upload schema), transcoding, video notes.

## 6. Verification material

`tests/test_forward_send.py` and `tests/test_text_replies.py`; pinned `td_api.h` field sets
(`tests/test_tdlib_media_schema.py` pattern).

## 7. Who decides

Deterministic throughout; the owner decides in the dialog. Sequential implementation (shared
broker/schemas/tdjson).

## 8. Risks and degradation

Unusual but valid files refuse (`unsupported_video`) rather than being sent with wrong metadata.
Large uploads may exceed the 120 s wait ⇒ `outcome_unknown` + status reconciliation. Telegram may
re-encode; status evidence reports what the provider returned.

**Ceiling:** three distinct failed hypotheses on one sub-step ⇒ stop and record.

### Amendments 16.10.2026 (critic review)

Lead decisions on the F15a critic findings; each has a test that failed before the change.
Where they conflict with §2–§3 above, these amendments win.

- **M1 — the attempting call never reports `expired`** (`send_prepared_video` and `send_prepared_artifact`,
  including artifact replies; `send_prepared_text` is unchanged). If artifact authority, scope or account
  checks fail after the claim — the post-send owner check, the publication `check_account`, or an
  `ArtifactUnavailable` reaching `_dispatch` — the broker consults the draft registry by draft id, calling
  client and send-tool kind (`attempt_outcome`): never claimed ⇒ `expired` as before; a claim that ended
  in a local failure ⇒ that content-free result (`local_failed` for video, `failed` with "no provider send
  was attempted" for artifacts); any other claim ⇒ `outcome_unknown` with "current receipt authority is
  unavailable; do not retry automatically". Provider evidence (status, message id) is never disclosed
  under lost authority; it stays in the registry and only a later call that still holds the original
  client lifecycle and account epoch replays it. Another client, or the other send tool, still sees
  `expired`. The internal receipt keeps the real outcome for `get_send_status`. A *later* call that no
  longer holds the original authority (client lifecycle, account epoch, and for replies provider epoch and
  capabilities) keeps the existing content-free `expired` replay refusal and never resends: the
  reply-artifact suites pin that refusal for every `send_prepared_artifact` replay without full
  authority, and the video tool matches it.
- **Selection tokens on unsupported operations.** A `selection_id`/`reply_selection_id` in the payload of
  an operation without selection support (including both video tools) is refused as `invalid_request`
  under every policy, before any selection, artifact or provider work (previously a `KeyError` escaped
  with `retained_selections` enabled).
- **I1 — final message correlation.** Replaces the §3 sentence "additionally check duration/width/height
  and file size": as for document and photo sends, `sending_id` + chat + temporary message id + a final
  `messageVideo` carrying a `video` object decide `sent`; provider re-encoding no longer turns a
  delivered video into `outcome_unknown`. The registration still carries the reviewed facts (bounded) but
  they are not compared and nothing new is recorded in the closed status models.
- **L1 — preview before insertion.** The video preview is built and validated from the exact candidate
  before the draft is inserted, so a refused preview leaves no orphan draft and supersedes nothing.
  `_safe_display_name` applies NFKC before splitting on `/` and `\`, so U+FF0F, U+FF3C or U+FE68 cannot
  become a separator after the split; this applies to every artifact-backed draft name (a document named
  `a／b.txt` is now `b.txt` instead of failing at staging).
- **L4 — dialog spans.** The video dialog encloses the file name and caption in « » rendered by
  `readable`, under the same `READABLE_RULE` legend line as the forward dialog; a literal « or » inside
  a span is marked.
- **L5 — declared facts.** The dialog groups duration, dimensions, codec, audio and streaming under
  "Declared by the file (not decoded):", and the `VideoDraftPreview` description (the
  `prepare_video_send` output schema) says the same. Existing tool schemas are unchanged.

**Residual risks accepted without code change:**

- **L2 — probe reopens the path.** The probe reads the cached artifact path after the store lookup; the
  draft binds sha256 and size, and claim and staging re-hash the bytes, so only a same-user rewrite of the
  owner-only cache between probe and hash could pair facts with other bytes. The facts are declarations
  (L5) either way.
- **L3 — provider lock hold.** The video send holds the serialized provider lock for its confirmation
  wait of up to 120 s; other provider operations queue behind a slow upload.
- **L6 — final caption not compared.** As for plain artifact sends, the final message's caption is not
  compared with the draft caption; correlation decides.
- **M1 scope.** Only the attempting call is covered. A client that ignores its `outcome_unknown` and calls
  again after a release or account switch reads `expired` and could prepare a duplicate; extending the
  registry consult to later calls would rewrite the pinned reply-replay refusals (owner decision).
- **Unpublished prepare.** If the publication check fails after a successful `prepare_video_send`, the
  inserted draft (which superseded any pending one for the same artifact and recipient) is never returned
  and expires unused; as for every artifact-backed prepare.

### Amendments 16.10.2026 (docs alignment)

- At send the artifact is re-hashed (`peek`) before the recipient is re-resolved; both happen
  before the dialog, so the order is immaterial to safety.
- A zero-byte artifact also reports `video_too_large` (the size check is `0 < size ≤ 64 MiB`);
  unreachable through uploads, which need at least one byte.
- `get_send_status` for a video draft without `video_send` returns the content-free unknown shape.
