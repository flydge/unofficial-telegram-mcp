# 0.55 — multiple accounts (F16) — implementation spec

**Status:** lead spec, 21.10.2026, written under the owner's standing delegation. Every decision below is a
**lead decision, owner review pending** (see the [completion plan](completion-plan.md)).
**Branch:** `multi-account-055`, from the 0.54 release candidate.
**Tasks:** [`0.55-multiple-accounts-spec.tasks.md`](0.55-multiple-accounts-spec.tasks.md)
**Requirement:** F16 ([initial roadmap](initial-roadmap.md)): trusted local aliases with separate sessions,
sockets, locks and caches; every handle and receipt bound to its account; validation with two really
authorized accounts.

## 1. One sentence

The owner can add a second Telegram account under a short local alias:
- it gets its own session, broker, LaunchAgent, caches and client entries;
- a handle from one account is never accepted by another;
- the approval dialog names the account;
- an install stays byte-identical to 0.54 until its first `account-add`, with the same paths, names, files
  and schema fingerprint (amended 24.10.2026, A1).

## 2. Model

- **Alias.**
  - Grammar: a closed token `[a-z][a-z0-9]{0,11}`.
  - `default` is reserved and means today's single account in today's paths.
  - An alias is fixed in the client registration's argv. It is never a tool argument, an environment
    variable or a path.
  - `TELEGRAM_SEARCH_PROFILE` keeps its legacy meaning and is not reused.
- **`AccountPaths`.** A frozen dataclass in `config.py`.
  - Fields: root, session (`tdlib`, `db`, `files`), `run`, socket, broker lock, connect lock and status,
    artifacts, uploads and staging (each with its quarantine sibling), runtime policy, enrollment record,
    broker label and plist, connect label, MCP server name.
  - `AccountPaths.for_alias('default')` returns exactly the current module constants. The constants and
    `_owner_paths` stay.
  - `SetupPaths` is derived from it. The exact-type checks accept the derived form.
- **Non-default roots.** Siblings of the legacy tree, never inside it:
  `~/Library/Application Support/TelegramSearchMCP-accounts/<alias>/`.
  - 0.52–0.54 never read them, and the default tree is never touched.
  - When an alias is added, and again whenever a listed alias is admitted, the socket path is checked
    against the macOS 103-byte limit. A violation is refused with the fixed code `alias_path_too_long`
    (amended 24.10.2026, A3).
  - The tool-name budget (`mcp__telegram_search_<alias>__<longest tool>` ≤ 64) is checked at the same time.
- **Registry.** `TelegramSearchMCP-accounts/registry.json`, owner-only, with a closed schema:
  `{"version": 1, "aliases": {"<alias>": {"user_id": int|null}}, "default_user_id": int|null}`.
  - It exists only after the first `account-add`, and outlives the last alias's removal until a rollback
    below 0.55 or an uninstall with no alias left retires it (amended 24.10.2026, A1). Without it, every
    code path behaves as in 0.54 but the dialog's two substitutions in §3C.
  - Each broker pins its Telegram user id at its first authorized `getMe`. A later mismatch blocks with
    `account_mismatch`.
  - The same user id under two aliases, the default included, is refused with `account_duplicate`.
  - The user id is never printed, logged or returned.
- **Labels and server names.**
  - Broker label: `<service>.a.<alias>.broker`. Connect label: `<service>.a.<alias>.connect`.
  - MCP server name: `telegram_search_<alias>`.
  - The default keeps `<service>.broker`, `<service>.connect` and `telegram_search`.
- **Wire contract unchanged.**
  - No handshake key, tool parameter or response field is added. The schema fingerprint is unchanged, and
    that is part of the gate.
  - The proxy reaches its broker only through its alias's socket.
  - The alias reaches the model in two places, neither of which enters the fingerprint:
    - the MCP `serverInfo.name`, `telegram-search-mcp-<alias>` (distinct from the client server name
      `telegram_search_<alias>`);
    - one instructions line ("This server serves the account alias «work». Run telegram-search-transfer with
      --account work for its artifacts and uploads."; amended 24.10.2026, A2 and A13).

## 3. Work items

### A — paths (behaviour-neutral)

- Add `AccountPaths`.
- Thread it through every constructor and call site that defaults to an import-time constant:
  - broker, `launch_agent.run_broker`, `TDLibClient.from_defaults`;
  - `ArtifactStore`, `LocalUploadRegistry`, the staging root and the staged-path comparison in `tdjson.py`,
    the download containment root;
  - proxy `server.py` (socket, policy, artifact root), `transfer_cli.py`;
  - `BrokerClient.restart_callback`, the connect flow and `setup_cli`.
- The Whisper model stays shared.
- Gates:
  - Golden test: the default alias equals literal 0.54 paths and names.
  - AST sweep: no module outside `config.py` defaults a parameter to a path, label or socket constant.

### B — registry, grammar, pin

- Registry module with a closed parser, atomic owner-only writes under a lease, and bounded size
  (≤ 8 aliases).
- Launcher grammar: `mcp --account <alias>`, `broker --account <alias>`, and `--account <alias>` on
  `setup`, `resume`, `connect`, `wait`, `cancel`, `api-credentials`, `status`, and (phase D)
  `capabilities show|enable|disable <profile> --account <alias>` (amended 24.10.2026, A5).
  - The alias is validated against the registry before any directory is created. Without the flag, the
    action is the default alias, with byte-identical argv.
- `server.py --account`, the same option on `telegram-search-transfer`, and the plist `ProgramArguments`
  for alias brokers.
- Account pin and duplicate refusal, enforced at authorization, at every login before the handoff, and
  before every broker operation outside a closed exempt set (amended 24.10.2026, A4).

### C — broker, connect, dialog

- One broker and one LaunchAgent per alias. The connect job is per alias, and the QR page names the alias.
  The default stays as is.
- The approval dialog names the alias and a masked account for every kind once a registry exists. Without
  a registry the 0.54 dialog is unchanged except that a chat whose id is the account's own reads "Saved
  Messages" and a forwarded own message's sender reads "you" (in both modes; amended 23.10.2026 after the
  phase C review). Once a registry exists the summary and chat labels never print the account's id; without
  one the 0.54 `Account: <user id>` line stays (amended 24.10.2026, A6). A reply target's rendering
  shows the source data as it is, so a source that mentions the owner by name still carries that id.
- Once a registry exists, 0.54's one owner dialog at a time holds across every broker of the user: each holds
  a non-blocking flock on the owner-only `TelegramSearchMCP-accounts/dialog.lock` for its whole dialog, and
  while another broker holds it, or it is unsafe, a send or apply answers `dialog_unavailable` as the in-broker
  rule does. Without a registry nothing is read or created there (amended 24.10.2026, A12).
- Re-login hardening inside one broker: bind the discovery cursor (`scan_`) to the account and generation,
  and make `attempt_outcome` and `is_owned_*` owner-aware.

### D — clients and installer

- Registrations take an optional server name, defaulting to today's.
  - Codex alias entries use `required=false`.
  - Claude Code alias entries are user-scope.
  - Claude Desktop entries are neighbours.
  - The plugin stays default-only. In plugin mode, alias entries are user-scope with distinct names, so
    no tool set is listed twice.
- `account-add <alias>` and `account-remove <alias>` are small journaled transactions run from the
  installed release.
  - They write or remove the alias's client entries and update an `accounts.json` sidecar in the
    installation root, modelled on `adopted.json`.
  - They run only from the current release, one that knows aliases (`release_not_current`; 055d review).
  - account-add creates the alias root (owner-only, empty but for `run/`) right after its registry entry; nothing
    else creates it (055d3 review). Before its transaction it judges the accounts folder it writes into, also
    without a registry (`registry_unsafe`), and a loaded default broker that does not answer its one check is
    reported (`default_check: unanswered`) without stopping the add (amended 24.10.2026, A15).
  - Removal boots out the connect job, then the broker (gated again) and unlinks its exact plist, both again
    on every attempt until the root moves, and moves the alias root aside (amended 24.10.2026, A7). It never
    deletes. account-add's repair path rewrites an alias plist of another release of this installation to the
    current release's (055d2 review), and moves the alias's runtime.toml version line onto the current release
    from an equal or older release, keeping its session (055d4 review); a newer release's line refuses
    `policy_conflict` before the transaction (amended 24.10.2026, A9).
  - Rename is a remove plus an add, because the enrollment binds absolute paths.
- Every installer transaction that touches aliases (upgrade, rollback, uninstall, account-add, account-remove)
  holds every alias's connect.lock for each run, fresh or resumed, the lock every login holds for its whole run
  (the connect helper and `setup`/`resume --account`). So no alias login runs during a run, and a running one
  refuses `login_in_progress` with nothing changed (055d and 055d2 reviews), naming the alias (`account`); a lock
  that no login holds but is unsafe refuses `connect_lock_unsafe`, naming it too (amended 24.10.2026, A14).
  account-add holds its own alias's only on its repair path, where the registry already lists it (055d4 review).
- An alias login never creates the alias root and never runs while an installer transaction is pending (055d3
  review):
  - `connect`, the connect helper, `setup`, `resume`, `cancel` and `api-credentials --account` take the connect.lock
    only inside the existing root, creating at most `run/`, and read the registry before and once it is held. A
    missing root or an alias no longer listed refuses `alias_unavailable` with nothing created.
  - Run from an installed release, `connect`, the connect helper, `setup` and `resume` (the last three also
    right before their handoff) refuse `transaction_pending` while a first install, upgrade, rollback,
    uninstall, account-add or account-remove is unfinished (amended 24.10.2026, A11), changing nothing. The
    refusal names the action and an account action's alias (`pending_action`, `pending_account`), as the
    installer's own does (055d4 review). They also refuse while the alias's runtime.toml names another release:
    `newer_state_kept` for a newer one (or one outside the version grammar), `older_state_kept` (next action
    `run_account_add_for_alias_then_retry`) for an older one (amended 24.10.2026, A16). The default's login and
    source mode keep 0.54's behaviour.
- An alias plist exactly of this installation's own shape, naming any of its releases (present or not), is the
  installer's: upgrade, rollback and account-add rewrite it, account-remove and uninstall remove it. Anything else
  stays foreign: `service_conflict`, never removed (055d2 review).
- Upgrade, rollback and uninstall loop over the default and every alias:
  - one service step per alias, with per-alias journal keys;
  - a pending-send gate per loaded broker, where any `unknown` blocks; uninstall gates every broker in one pass
    before any bootout, and runs each alias's connect job bootout and broker step again on every attempt;
  - a loaded alias broker whose definition's interpreter is gone (a release since removed) is gated through its
    live socket under the current release: a stale socket holds nothing, a broker that answers is gated as usual,
    and one that cannot be read refuses `alias_broker_unreadable`, naming the manual bootout of its exact label
    (055d3 review);
  - alias plists rewritten before an old release is retired;
  - a per-alias state check on rollback, run again for an alias whose plist appeared between two runs: a newer
    session keeps that alias on its release (`newer_state_kept`; 055d2 review). Its plist, which names a release
    the receipt no longer names, is set aside into the transaction, so nothing runs it: the alias stays offline until
    the next upgrade or its account-remove, and its login from the current release refuses `newer_state_kept`
    (055d3 review).
  - Rollback to a release older than 0.55 refuses with `accounts_present` while any alias exists. With none
    left it retires the registry and the default's readiness record once the older broker serves; an
    uninstall with no alias left retires the registry; the last alias's account-remove retires accounts.json
    into its transaction (amended 24.10.2026, A8).
- `status` reports every alias: loaded, authorized and registered, never the account. An entry left to the owner's
  printed command counts once it is exactly there (055d2 review).

### E — isolation matrix

- Two real brokers on short injected roots, with fake TDLib clients returning different user ids.
- Every handle kind minted on A and presented to B must get the same fixed refusal as an unknown handle:
  - the eight draft kinds: text, artifact, reply text, reply artifact, forward, video, archive and text edit
    (amended 24.10.2026, A10);
  - send status;
  - artifact, including the transfer download;
  - upload id, authority and result tokens;
  - selection;
  - verified target;
  - nine cursors plus `scan_`.
- Also tested:
  - socket-length and tool-name refusals;
  - the duplicate account and pin mismatch;
  - two aliases in one LaunchAgent domain with label disjointness.

### F — docs and critic

- An "Accounts" section in `docs/install.md`; `docs/reference.md`; the setup skill and its plugin copy;
  the security notes (same-UID trust, N × 1 GiB cache, one TDLib per alias).
- An independent critic.

### G — owner, at the end

- Add a second account by QR. Approve one action per account. Check that the dialog names the right one.

## 5. Out of scope

Running two accounts in one broker. Moving the default account to a named alias. Per-alias plugin
entries. Changing the default capability profile.

## 6. Decisions and rejected options

- **Sibling roots, not `accounts/` inside the legacy tree.** Nesting keeps the tree together, but a rollback
  to 0.52 would then see unknown entries in its root, and the socket budget would shrink further.
- **One Keychain service.** The `api_id`/`api_hash` pair is the application's identity, so sharing it is
  correct. Database keys are already unique per enrollment.
- **No handshake or schema change.** An alias field in the descriptor would change the default's exact key
  set and fingerprint. The socket path already binds the account.
- **Alias in argv only.** Registrations, plists and the plugin shim are closed to environment variables.
- **The plugin stays default-only.** A plugin cannot carry a per-user argument without an unverified
  user-config spike.
- **Removal moves aside.** Permanent deletion of session data is never automated.

## 7. Risks

- Hot files (`config.py`, `broker.py`, `tdjson.py`, `launch_agent.py`, `bundle_install.py`) change together.
  Phases A–D run sequentially in the auth/session lane.
- Long home paths can exhaust the socket budget for aliases. They are refused with a fixed code, never
  truncated.
- Client allowlists keyed on `mcp__telegram_search__*` do not cover alias servers, so the docs say so.

**Ceiling:** three distinct failed hypotheses on one sub-step ⇒ stop and record.

## Amendments 24.10.2026

Reconciled with the code at the end of phase D (review rounds 055d to 055d4 and the lead decision after
055d4) while the phase F docs were checked against it. Each item is a **lead decision, owner review
pending**; the sections above carry the matching in-place corrections, marked "amended 24.10.2026".

- **A1 — byte-identity and the registry's lifetime (§1, §2).** An installation is byte-identical to 0.54
  until its first `account-add`, not whenever no alias exists. `account-remove` keeps `registry.json`, so
  after the last alias goes the default's pin stays, the dialog keeps naming «default», `status` keeps
  `accounts` and the default broker keeps writing `run/readiness.json`; only a rollback below 0.55 or an
  uninstall with no alias left retires the registry. An alias that never logged in keeps a root holding only
  `run/` (plus the `run/connect.lock` any later installer transaction held), which its account-remove moves
  aside (`session: moved`). Lead decision, owner review pending.
- **A2 — the alias reaching the model (§2).** The instructions line ends with a period ("This server serves
  the account alias «work».", extended by A13) and `serverInfo.name` is `telegram-search-mcp-<alias>`, distinct
  from the client server name `telegram_search_<alias>`. Lead decision, owner review pending.
- **A3 — the socket budget (§2).** Checked at `account-add` and again at every admission of a listed alias:
  `account_registry.admits` refuses `alias_path_too_long` for a hand-written registry entry. The installed
  launcher maps every registry refusal to `alias_unavailable`; `telegram-search-setup --account` passes
  `alias_path_too_long`, `registry_invalid` and `registry_unsafe` through. Lead decision, owner review
  pending.
- **A4 — where the pin is enforced (§3B).** Not "before every Telegram-sourced handle grant" but before every
  broker operation outside the closed exempt set `health`, `release_client`, `check`, `create_local_artifact`,
  `begin_local_upload`, `append_local_upload` and `finish_local_upload` (the upload-authority operations are
  routed before the check, being owner-local bytes); a new operation is checked by default. Every login applies
  the same rule before its handoff (phase C decision 2). Lead decision, owner review pending.
- **A5 — grammar and code families (§3B, §3D).** `capabilities show|enable|disable <profile>` with a
  trailing `--account <alias>` joined the launcher grammar in phase D. `alias_unavailable`, `account_mismatch` and
  `account_duplicate` are launcher, login and transfer codes, not installer codes (not in `INSTALL_CODES`).
  `alias_invalid` is in `INSTALL_CODES` but the launcher never prints it: an alias outside the grammar fails
  the launcher grammar first (`bundle_admission_or_install_failed` for the account actions,
  `bundle_admission_failed` for the others). `newer_state_kept` and `rewritten` are result outcomes, not
  installer codes; `newer_state_kept` is also a login code, as is `transaction_pending`. Lead decision,
  owner review pending.
- **A6 — the dialog's account line (§3C).** "The summary and chat labels never print the account's id" holds
  once a registry exists. Without one the default's dialog keeps 0.54's `Account: <user id>` line
  (`approval_prompt._account_line`). Lead decision, owner review pending.
- **A7 — removal (§3D).** Not "boots out the broker": the connect job goes first (its handoff loads the
  broker), then the broker is gated again, booted out by its label and its exact plist unlinked; both run
  again on every attempt until the root moves and once more right before the move (review fix 055d). Lead
  decision, owner review pending.
- **A8 — retirements (§3D).** A rollback below 0.55 with no alias left, once the older broker serves again,
  moves the registry aside to `TelegramSearchMCP-accounts/retired-<32 hex>-registry.json` and the default's
  `run/readiness.json` into its transaction (`account_registry: retired`); an uninstall with no alias left
  moves the registry aside the same way; the account-remove of the last alias retires `accounts.json` into
  its own transaction directory. Nothing is deleted. Lead decision, owner review pending.
- **A9 — the repair path's version line (§3D).** account-add's repair path moves an alias's `runtime.toml`
  version line onto the current release only from an equal or older release, not "from any value". A newer
  release's line (a lower version installed after an uninstall) refuses `policy_conflict` before the
  transaction with nothing changed: a session a newer release served is never handed to an older one, the
  rollback's rule (`newer_state_kept`). The owner installs that release again or removes the account (lead
  decision after 055d4, aeaa0e7). Owner review pending.
- **A10 — draft kinds (§3E).** The isolation matrix covers eight draft kinds (text, artifact, reply text,
  reply artifact, forward, video, archive, text edit), not seven. Lead decision, owner review pending.
- **A11 — pending first install (§3D).** A login's `transaction_pending` also covers an unfinished first
  install (`pending_action: install`), and unreadable transaction state counts as pending, naming nothing.
  Lead decision, owner review pending.

## Amendments 24.10.2026 (critic fixes 055f)

The independent 0.55 critic's confirmed findings, fixed after the amendments above (task record, phase F,
"Critic fix (055f, …)"). Each item is a **lead decision, owner review pending**.

- **A12 — one dialog across brokers (§3C).** 0.54's one-owner-dialog rule held per broker only, so two
  account brokers could stack identical dialogs. Once a registry exists every broker of the user also holds
  a non-blocking flock on `TelegramSearchMCP-accounts/dialog.lock` (created `0600` only inside the existing
  owner-only folder, never creating it; an existing one must be an owner-owned `0600` regular single-link
  file and is never changed) for its whole dialog. Held by another broker, or unsafe: `dialog_unavailable`
  exactly as the in-broker rule (no dialog, no attempt, the draft pending, not counted as an open dialog).
  Without a registry nothing is read or created there. Rejected: a lock created by account-add (a broker
  would then depend on an installer step for a safety rule) and a blocking wait (it would queue a dialog
  behind the open one, which 0.54 forbids). Accepted gap: a dialog already open when the first account-add
  runs holds only its broker's lock, at most until its 120 s timeout.
- **A13 — the instructions line (§2).** The alias's line also tells the model to pass `--account <alias>` to
  `telegram-search-transfer`, whose default is the default account's broker and cache; it stays outside the
  schema fingerprint. The search skill is left as it is (its 20,000-byte budget had 92 bytes left).
- **A14 — login locks in installer refusals (§3D).** `login_in_progress` (a held connect.lock or a running
  connect job) carries `account`, the alias as a closed token, as `alias_broker_unreadable` does. A lock,
  run folder or alias root that is unsafe is no running login, so `wait` and `cancel` cannot clear it: it
  refuses the new installer code `connect_lock_unsafe` (also with `account`), nothing changed or repaired;
  the owner restores the shape by hand (`chmod 700` the folders, `chmod 600` the lock). Rejected: repairing
  the lock automatically (the installer never changes a file it does not own the shape of).
- **A15 — account-add (§3D).** A loaded default broker that does not answer account-add's one check is
  recorded and reported as `default_check: unanswered` and the add continues, as for `not_loaded` (the known
  limit about an alias logging into the default's account first then applies); `ready` and `blocked` are
  unchanged and `default_check_failed` is gone from the installer's codes. Rejected: probing the default
  broker before the transaction (the check must run after the registry entry, so that the default pins
  under the registry the alias joins) and letting account-remove take over an unfinished add (a second
  resumption path for one transaction). The accounts folder a new alias's add writes into is judged before
  the transaction opens (`account_registry.check_root`): absent, or owner-only and reached without a link,
  even without a registry; otherwise `registry_unsafe` with nothing changed and nothing pending.
- **A16 — an older alias line at login (§3D).** `login_admission` compares the alias's runtime.toml version
  with the running release in the one release grammar's PEP 440 order (`bundle_runtime.release_order`,
  which the installer's `_version_key` wraps): an older line (an uninstall kept the alias and a newer
  release was installed since, before account-add's repair) refuses the new login code `older_state_kept`,
  next action `run_account_add_for_alias_then_retry`; a newer line, or one outside the grammar, keeps
  `newer_state_kept`. `older_state_kept` is a login code only, in the connect and setup tables (A5).

Not amended, recorded for the final audit (not 0.55's): a first install never moves the default's own
`runtime.toml` version line, so an uninstall and a reinstall at another version meets `config_stale` and
then `policy_conflict`. This is the 0.53/0.54 behaviour, left unchanged under criterion 2
([final acceptance tasks](final-acceptance-spec.tasks.md)).
